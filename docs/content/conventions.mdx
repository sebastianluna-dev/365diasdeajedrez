# Conventions

These rules are enforced by review, a few tests (`proxy.test.ts`, `nav-items.test.ts`, `components/platform/border-radius.test.ts`, `components/platform/platform-tokens.test.ts`, `components/reduced-motion.test.ts`, `components/ui-verbs.test.ts`, `components/stories.test.ts`, `components/platform/type-and-space.test.ts`, `components/platform/breakpoints.test.ts`) and habit rather than by tooling, so read them once and keep them close. `AGENTS.md` (loaded as `CLAUDE.md`) carries the short version; when the code and a rule disagree, the code wins and the rule should be fixed.

## Files and modules

- **kebab-case** for every file: `study-card.comp.tsx`, `use-chess-clock.hook.ts`, `auth.const.ts`. Suffixes say what a file is: `.comp.tsx` (component), `.section.tsx` (page section), `.hook.ts`, `.const.ts`, `.service.ts`, `.mapper.ts`, `.types.ts`, `.actions.ts`, `.test.ts`.
- **Named exports** everywhere. Default exports only where the App Router requires them (`page.tsx`, `layout.tsx`, `route.ts`, `error.tsx`…).
- **No barrels** (`index.ts` re-exports). Import the concrete file with the `@/` alias: `@/services/studies/studies.service`.
- The App Router files stay thin: a page resolves params, calls a service, and renders sections.

## Components

- **Platform form controls are built on [Radix Primitives](https://www.radix-ui.com/primitives)** (the `radix-ui` package: unstyled, drawn with the project's BEM and tokens; never Radix Themes) through the shared pieces `PlatformForm`/`PlatformFormField`/`PlatformFormGroup`, `PlatformSelect`, `PlatformChoiceCards` (one of a few, as cards) and `PlatformCheckCards` (several of a few, as cards) in `components/platform/shared/`. A new form uses them; forms still on `FormField` with native controls are migrated as they are touched. Dialogs stay native `<dialog>`, which is why the select's list is not portalled.
- **Reordering by dragging is [dnd-kit](https://dndkit.com)** (`@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/modifiers`, `@dnd-kit/utilities`), set up once in `SortableDnd` (`components/platform/sections/staff/courses/sortable-dnd.comp.tsx`): sensors, the sortable context, the modifiers that keep a row in its list, and the announcements, which are written in Spanish because the library's own are English. The rows only ask `useSortable` where they are, and the order itself — optimistic, saved in a transition — stays in `useSortableRows`. The sortable lists of the staff panel are drawn with it: the syllabus of a course and of a chapter (`SyllabusList`) and the games of a chapter's collection (`ChapterGameList`). `GameList`, in a study, still moves on the browser's own drag events.
- **Server Components by default.** `"use client"` goes only on the leaf that owns state or browser APIs (the game viewer, the board, the header dropdown, the upload widget…).
- **A new component receives data, not components.** No props of type `ReactNode`/`ReactElement` that the page fills with JSX (`editGame={<EditGame … />}`, `studyTools`, `share`…): the component receives the model (`study`, `game`, the catalogs) and decides for itself what it mounts and under which permission. The one exception is `children` on a container whose only job is to place what it is given (a layout, a card, a dialog). When one part needs state, split by data ownership: the wrapper stays on the server and only the stateful leaf is a client component (`GameAside` + `GameList`); never turn everything into a client component to be able to pass slots. Components older than this rule that still take slots (`GameViewer` with `skip`/`footerActions`/`positionActions`, `PlatformFormField` with its required `children`) are reworked as they are touched.
- **The markup's accessibility is linted.** `npm run lint` runs the recommended `jsx-a11y` rules as errors, so a click handler on an element that is not a control, a `role` without what it requires or a `<label>` without its control fail CI. A deliberate case keeps the rule and says why on the line: `// eslint-disable-next-line jsx-a11y/<rule> -- <reason>`, the reason being what the element is, not that the rule is wrong.
- Images always go through `next/image`; never a raw `<img>`. Remote images are limited to `res.cloudinary.com` (`next.config.ts`), and `lib/remote-image.ts` guards user-typed URLs before they reach `next/image`.
- **One action, one verb**: «Agregar» puts something into a set, «Quitar» takes it out of where it is without destroying it, «Eliminar» destroys it; «Añadir» and «Borrar» are not written. A hint or an error uses the verb of the button it is about, and a `pendingLabel` is a gerund with «…». The table is in the [Glossary](/glossary#verbs-of-the-interface), and `components/ui-verbs.test.ts` fails on a verb that lost.
- **Every shared piece of the platform has a story.** A piece of `components/platform/shared/` lives in a folder of its own beside `<name>.stories.tsx`, with one story per state that matters. In any stories file, the `title` is its path with the product first and the export name in place of the component's folder (`platform/shared/PlatformNotice`), every story has a JSDoc line (`/** … */`) that says what it shows, and its component's page in `docs/` names the file in a «Story» row right after «Stylesheet». Every story titled `platform/…`, `chess/…` or `icons/…` also has its tile on the [overview sheet](/ui/storybook#overview) (`platform/Overview`), which draws it with sample data and links to its Docs page. `components/stories.test.ts` holds the folder, the file, the title, the JSDoc, the row and the tile, on every stories file of the repository but the pages' (the overview, the foundations, the primitives and the icon gallery, which name the page); the states are a matter of review. `ImageUpload` is its one listed exception until its server action can be mocked. How to write one: [Storybook](/ui/storybook).
- Copy shown to users is **Spanish**, including URLs (`/estudios`, `/profesor/alumnos`). Dynamic segment names (`[courseId]`) stay in English because they are code identifiers and never appear in the address bar.
- **Every comment is written in English**, wherever it lives: code, CSS, tests, scripts, `prisma/schema.prisma`, workflows, `.env.example`, `.gitignore` and any other configuration file; like every other identifier. A comment that quotes a label, a URL parameter or a catalog value keeps it verbatim in Spanish, because that is the string in the product. The one exception is generated files: `payload-types.ts` reproduces the CMS field descriptions, which are copy, and is never edited by hand.
- `components/` mirrors the products in `app/`: `site/`, `platform/` and `auth/`. Inside each product, `sections/` holds the page sections (`.section.tsx`, with the `.comp.tsx` pieces only they use) and `shared/` the pieces several of that product's sections reuse; `chess/` (board, viewer, diagram) and `icons/` serve every product. There is no `common/` folder: a piece belongs to one product or to the chess domain.

## CSS

- **Strict BEM, Yandex flavour:** `block__element`, modifier `_key_value` (`platform-table__head_align_right`), boolean modifier `_open`.
- **One CSS file per component**, imported by that component, and **every rule nested under the root selector** with native CSS nesting (`&`). Media queries go inside the block. Nothing global except `globals.css`, `platform.css` and the intentional `.blog-button` helpers.
- **Desktop-first** media queries, and **only Tailwind's five breakpoints**: 640, 768, 1024, 1280 and 1536px, written in the range syntax — `@media (width < 1024px)` below one, `(width >= 1536px)` from one. A height is not a breakpoint and stays free. `components/platform/breakpoints.test.ts` holds it.
- Colours and spacing come from tokens: `--color-*` in `app/(frontend)/globals.css` (public site, plus board colours `--board-light`/`--board-dark`) and `--platform-*` in `app/(platform)/platform.css` (private area). A bare hex value in a component stylesheet is debt. The platform's and the access pages' stylesheets have none; the ones that remain are in the public site's stylesheets and in `components/chess`, where all but `EloTable`'s are the fallback of a `--platform-*` token (`var(--platform-surface, #2b2723)`) for the public site, where those tokens do not exist. No task tracks them.
- **The platform has two themes, and a colour is written as a pair.** Every `--platform-*` colour is declared with `light-dark(<light>, <dark>)` in the one `:root` block of `platform.css`; adding or correcting a colour means touching one line, and the two values are always read together. Which of the two applies is decided by `color-scheme` on `:root` — `light dark` by default, so the platform follows the machine, and `light`/`dark` when `:root[data-theme]` says the person chose (see [Themes](/architecture/themes)). **`color-scheme` must stay on the same element as the tokens**: Turbopack compiles `light-dark()` through Lightning CSS into helper variables declared wherever the `color-scheme` is, and declared one element below they never reach the tokens above them.
- **A text reaches 4.5:1 on what it is written on, in both themes.** The subtle grey (`--platform-text-subtle`) is for the white surfaces only (`surface`, `surface-soft`); on a grey or tinted fill (`bg`, `surface-neutral`, `surface-sunken`, the accent's soft and wash) the text is `--platform-text-muted`. `components/platform/platform-tokens.test.ts` reads the stylesheets and fails on a colour that is not a pair, on a token that is used and not declared, and on a text colour under the minimum on its fill.
- **Font sizes and spaces come from the scales.** A `font-size` is one of the ten `--platform-type-*` tokens (12 to 52px) and a `gap`, `padding` or `margin` one of the twelve `--platform-space-*` (a 4px grid, 2 to 96px; a negative margin is `calc(-1 * var(…))`), never a px of its own. What stays in px: a 1px hairline, a px inside a `calc()` of geometry, and the board's coordinates (9px). The platform has no `zoom` since 2026-10-02: the steps carry the enlargement it gave, and from 1536px (`2xl`) every token takes a step up in one `@media` block of `platform.css`, which no stylesheet has to know about. The four chess stylesheets the public site also draws write each token with the site's size as its fallback. `components/platform/type-and-space.test.ts` holds it; the scales are drawn in Storybook and described in [Styling › Type and space](/ui/styling#type-and-space).
- **Whoever asks for less motion gets it everywhere.** A stylesheet that starts an animation stills it under `prefers-reduced-motion: reduce` (`animation: none`; cut to an instant, `animation-duration: 1ms`, when the component waits for `animationend`), and does the same with a `transition` that moves or resizes something (`transform`, a width, a height, a position; a colour that fades is not motion and is left to the hover rules of `globals.css`). The `reduce` block goes **after** the rule it answers: under `@media` a rule weighs what it weighs outside it, and of two that weigh the same the later one wins; `scroll-behavior: smooth` lives inside `prefers-reduced-motion: no-preference`; and code that passes `behavior: "smooth"` reads the preference with `matchMedia` first. `components/reduced-motion.test.ts` reads every stylesheet and component of both products and fails on the one that forgets.
- No Tailwind (it was removed), no CSS-in-JS, no CSS Modules.
- The full token list, the helper classes and worked examples are in [Styling & design tokens](/ui/styling).

## Data and authorisation

- The UI never imports Prisma or Payload. Pages call `services/<domain>/<domain>.service.ts`; the mapper returns the `*.types.ts` view model with labels and hrefs already built.
- Route hrefs come from `lib/platform-routes.ts` (`platformRoutes`, `teacherRoutes`, `staffRoutes`), never from template strings in components.
- Every platform page's **first `await`** is either a data service (which calls the DAL) or `getCurrentUser()` itself. Every `/profesor` page and action opens with `requireTeacher()`; every `/administracion` one with `requireStaff()`.
- A new route under `app/(platform)` must be added to `PROTECTED_PATH_PREFIXES` (`constants/platform/auth.const.ts`) **and** to the literal `matcher` in `proxy.ts`; `proxy.test.ts` fails if the two lists diverge, and also if a folder of `app/(platform)` is in neither.
- Restricted domains are catalog tables with a stable `code`. TypeScript mirrors them as `as const` objects in `constants/platform/*-codes.const.ts`; no TS enums, no Prisma enums.
- Lists with `@@unique([parent, order])` are reordered only through `services/shared/reorder.ts`.

## Server actions

- `"use server"` modules export **async functions only**; messages and constants live in `constants/platform/*-messages.const.ts`.
- Read form fields through a zod schema with `parseForm` from `services/shared/form-schema.ts` (`formText`, `formOptionalText`, `formOptionalUrl`, `formInt`, `formLenientInt`, `formCheckbox`, `formEmail`, `formTextIfPresent`, `formReturnTo`, `readIds` for the hidden ids); the schema is the action's contract, bounds every input and names the field that failed so the action answers with the code its page knows.
- Resolve the user first, then rate-limit with `allowAction(key, limit, windowMs)` (`lib/rate-limit.ts`), then validate, then write, then `revalidatePath`.
- Errors travel back as a redirect to the page with `?error=<code>` (`withErrorParam`), and the page translates the code with the message map. The only exceptions return state through `useActionState`: account creation and password reset, because a temporary password must never sit in a URL, and the «Autores» dialog, which stays open over the page and has to get the outcome back itself. A result worth telling travels the same way as an error, in a parameter of its own: the PGN imports redirect with `?importadas=<stored>.<without moves>.<over the limit>` (`withImportReport`), and the page reads it back with `readImportReport`, which gives nothing for a value that could not have happened, because anybody can type a parameter.

## Chess content

- The PGN is the content. Lessons, games and class blocks store PGN text; positions are derived at read time by `lib/chess`.
- A move inside a PGN tree is addressed by a **dotted path** of child indexes from the root (`"0.0.1.0"`). `TrainingExercise.path` and `ClassBlock.movePath` use it.
- Positions are identified by `createPositionHash(fen)` (`lib/chess/position-hash.ts`), computed on the server only.

## Documentation and debt

- Debt you find but do not fix goes to `IMPROVEMENTS.md` with area, priority (low · medium · high · extreme) and how to approach it. Mechanical, well-specified tasks go to `TODOS.md`. Risks the project accepts knowingly go to `WARNINGS.md` with what, why and the way out. The three are in English and **local only**: gitignored, never in the remote, so a fresh clone does not have them.
- **Every important change is documented in the same commit**, not afterwards: behaviour, a convention, a route, the data model, a script, an environment variable, or a decision worth recording. Edit the page of this site that covers the area you touched, and rebuild it (`cd docs && npm run build`) when its pages changed.
- `README.md` stays the quick reference of the repository, in English; this site is the long-form documentation.
- Before touching framework APIs, read `node_modules/next/dist/docs/`: Next 16 renamed middleware to `proxy.ts`, made `params`/`searchParams` promises, changed caching APIs and more.

## Coding agents

`.claude/settings.json` is the repository's Claude Code policy. It only restricts — it holds no `allow` rule — and a `deny` or `ask` rule wins over an `allow` in any other settings file, so it holds whatever your own settings say.

**Never** (`deny`):

- Reading or editing `.env.local` and `.env`. They hold the database URLs (the managed ones on commented lines), `PAYLOAD_SECRET` and the Cloudinary keys: edit them by hand. Prisma, Next and `scripts/` keep reading them, because the rule covers Claude's own file tools and the shell commands it recognises, not the programs it runs.
- `prisma migrate reset` and `prisma db push`: both throw data away, and the schema only moves through migrations.
- `docker volume prune`, `docker system prune` and `dropdb`: the local databases live in the `postgres-data` volume.
- A forced push, in any spelling the rules know (`--force…`, `-f`, a `+` refspec, `--mirror`): it would rewrite the published history and deploy it. If one is ever needed, the owner runs it.
- `gh repo delete` and `npm publish`.

**Ask every time**, also in auto mode (`ask`):

- `git push` and `gh pr merge`: every push to `main` is a Production deployment ([release order](/operations/deployment#release-order)).
- `npm run db:deploy`, `db:seed`, `user:create`, `user:password` and `collections:by-chapter`, and `prisma migrate deploy`, `prisma db seed` and `prisma db execute`: they write to whichever database `.env.local` points at.
- `docker compose down -v` (and `npm run db:down -- -v`), `docker volume rm` and `pg_restore`: they throw away or overwrite a database.
- `npm run db:backup`: it writes to no database, but it reads all of one — accounts and password hashes — onto the disk.
- `git filter-branch`, `git filter-repo`, `git reset --hard` and `git clean`: rewritten history and discarded work.
- `gh repo edit` (it can change the repository's visibility), scheduling a job (`CronCreate`, `CronDelete`) and editing `.claude/settings.json` or `.claude/settings.local.json`.

It also sets `disableBypassPermissionsMode`, so no session can skip the prompts, and turns Claude's attribution off (`"attribution": { "commit": "", "pr": "", "sessionUrl": false }`): no `Co-Authored-By` trailer on a commit, no "Generated with" line or session link on a pull request.

- Your own `allow` rules and your `defaultMode` go in `.claude/settings.local.json`, which git ignores. What auto mode should know about the environment (this repository is public; a push to `main` deploys Production) goes in your user settings, under `autoMode.environment` in `~/.claude/settings.json`: Claude Code never reads `autoMode` from a repository.
- The policy applies to sessions started at the repository root, where `.claude/` lives.
- An agent started with worktree isolation (or a `--worktree` session) works in a full checkout under `.claude/worktrees/`. `.gitignore` (which Prettier reads), the ESLint ignores, `tsconfig.json` and `vitest.config.mts` all leave that folder out, so the four checks of the main checkout never read another checkout's files.
- **`.mcp.json` offers one MCP server, Next's own for development** (`next-devtools-mcp`, the one Next's bundled guide `node_modules/next/dist/docs/01-app/02-guides/mcp.md` describes). With `npm run dev` running it finds the dev server (`nextjs_index`) and calls the tools that server exposes at `/_next/mcp` (`nextjs_call`): the errors of the page that is open, the routes, a server action by its id, whether a route compiles — without the `next build` that needs both databases. It also answers from the docs bundled with the installed Next (`nextjs_docs`). It is pinned to an exact version on purpose — the guide's `@latest` would run whatever is published that day — and Claude Code asks each person before using it: the approval is personal and lives in `.claude/settings.local.json`, never in the committed policy.
- The rules match the command as it is written. `git -C . push`, `bash -c '…'` or a program that opens `.env.local` by itself are not stopped, so the policy brakes the usual path; it is not a sandbox.

## Definition of done

```bash
npm run format:check && npm run lint && npm run typecheck && npm test
```

The same four checks CI runs, in the same order: the first that fails stops the job, so a file that drifted from Prettier hides every later result (`npm run format` fixes what `format:check` reports). Plus the documentation of whatever you touched, updated in the same commit, and `cd docs && npm run build` when its pages changed. Performance work is measured with Lighthouse against `npm run build && npm run start`, three runs, median.
