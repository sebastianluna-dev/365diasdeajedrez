# Conventions

These rules are enforced by review, a few tests (`proxy.test.ts`, `nav-items.test.ts`, `components/platform/border-radius.test.ts`, `components/platform/platform-tokens.test.ts`, `components/reduced-motion.test.ts`, `components/ui-verbs.test.ts`, `components/stories.test.ts`, `components/platform/type-and-space.test.ts`, `components/platform/breakpoints.test.ts`, `agent-policy.test.ts`, `services/shared/prisma-errors.test.ts`, `components/docs-line-counts.test.ts`, `components/icons/icons.test.ts`, `components/optional-mark.test.ts`) and habit rather than by tooling, so read them once and keep them close. `AGENTS.md` (loaded as `CLAUDE.md`) carries the short version; when the code and a rule disagree, the code wins and the rule should be fixed.

## Files and modules

- **kebab-case** for every file: `study-card.comp.tsx`, `use-chess-clock.hook.ts`, `auth.const.ts`. Suffixes say what a file is: `.comp.tsx` (component), `.section.tsx` (page section), `.hook.ts`, `.const.ts`, `.service.ts`, `.mapper.ts`, `.types.ts`, `.actions.ts`, `.test.ts`.
- **Named exports** everywhere. Default exports only where the App Router requires them (`page.tsx`, `layout.tsx`, `route.ts`, `error.tsx`…).
- **No barrels** (`index.ts` re-exports). Import the concrete file with the `@/` alias: `@/services/studies/studies.service`.
- The App Router files stay thin: a page resolves params, calls a service, and renders sections.

## Components

- **Platform form controls are built on [Radix Primitives](https://www.radix-ui.com/primitives)** (the `radix-ui` package: unstyled, drawn with the project's BEM and tokens; never Radix Themes) through the shared pieces `PlatformForm`/`PlatformFormField`/`PlatformFormGroup`, `PlatformSelect`, `PlatformChoiceCards` (one of a few, as cards, with a radio's ring), `PlatformCheckCards` (several of a few, as cards, with a square box), `PlatformCheckbox` (a single box and its label, for a value saved with a form's button) and `PlatformSwitch` (an on/off that takes effect the moment it is pressed; the whole row is the switch) in `components/platform/shared/`. Since 2026-10-06 there are no native checkboxes in the platform: a round mark means one of several, a square one means any of them. Every `<form>` of the platform that has fields is a `PlatformForm` and every field a `PlatformFormField` (or a `PlatformFormGroup`), Server Component sections included, which mount them as they are; there is no other field piece (`FormField` went on 2026-10-08). Dialogs stay native `<dialog>`, which is why the select's list is not portalled.
- **What is optional is marked; what is required is not** (2026-10-05). A field whose control may be left empty says «Opcional» in a thin pill right after its label ([`OptionalMark`](/components/platform/shared/optional-mark)), and the field piece draws it, reading its control's `required` (`isOptionalControl`): only a `<textarea>` or an `<input>` one types into, never a search box, a checkbox, a select or a set of cards, which always show a choice. A group of check cards that may be left with none ticked says it with `optional` on `PlatformFormGroup`, since a group has no `required`. Nobody writes «(opcional)» or «Opcional» in a label, nor repeats in it the rule of what is required («Contenido (selecciona al menos uno)», dropped on 2026-10-06): without «Opcional» the field or group already says it has to be answered, and the minimum is told by the error on saving. A form of several fields, all optional, says it once with [`OptionalFields`](/components/platform/shared/optional-fields) («Todos los campos son opcionales.») and its fields carry no mark. Labels are light — the text size, regular weight, the muted grey. `components/optional-mark.test.ts` fails on the word in any copy but the pieces that draw it.
- **Reordering by dragging is [dnd-kit](https://dndkit.com)** (`@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/modifiers`, `@dnd-kit/utilities`), set up once in `SortableDnd` (`components/platform/shared/sortable-dnd/sortable-dnd.comp.tsx`): sensors, the sortable context, the modifiers that keep a row in its list, and the announcements, which are written in Spanish because the library's own are English. The rows only ask `useSortable` where they are, and the order itself — optimistic, saved in a transition — stays in `useSortableRows`. **A drag always has a way without it**: «Subir» and «Bajar» move a row one place per click (`useSortableStep`, through the same `onMove` a drop calls, and announced by `SortableDnd`), because a drag is a path the pointer has to hold and WCAG 2.5.7 asks for single clicks; at the ends of the list the one that would leave it is disabled, not removed. Every sortable list of the platform is drawn with it: the syllabus of a course and of a chapter (`SyllabusList`, «Subir» and «Bajar» in each row's menu) and the games beside the board, of a student's study or of a chapter's collection (`GameList`, two arrows at the end of each row); none moves on the browser's own drag events any more.
- **Server Components by default.** `"use client"` goes only on the leaf that owns state or browser APIs (the game viewer, the board, the header dropdown, the upload widget…).
- **A `loading.tsx` reaches no Client Component**, however indirectly. The platform's pages carry a content security policy with a nonce (`proxy.ts`, `lib/content-security-policy.ts`), and Next stamps it on the scripts of a page and of a layout but **not** on the scripts a loading boundary's client code needs: they are written into the HTML bare, and the browser blocks them. Seen on 2026-10-05, when the study game's `loading.tsx` took a blank card from the module that also held the record's edit dialog and every load of the page logged a blocked script. What a fallback draws lives in files with no `"use client"` behind them — `BoardLoading`, `BoardSkeleton`, the two skeletons —, and `components/loading-boundaries.test.ts` walks the imports of every `loading.tsx` to keep it so.
- **A new component receives data, not components.** No props of type `ReactNode`/`ReactElement` that the page fills with JSX (`editGame={<EditGame … />}`, `studyTools`, `share`…): the component receives the model (`study`, `game`, the catalogs) and decides for itself what it mounts and under which permission. The one exception is `children` on a container whose only job is to place what it is given (a layout, a card, a dialog, a form field around its control: `PlatformFormField` places the label, the control and its messages, and reads the control's `required`). When one part needs state, split by data ownership: the wrapper stays on the server and only the stateful leaf is a client component (`StudyAside` + `StudyGames`); never turn everything into a client component to be able to pass slots. A component older than this rule that still takes slots is reworked when it is touched (`GameViewer` lost its own, `footerActions`/`positionActions`, on 2026-10-08).
- **The markup's accessibility is linted.** `npm run lint` runs the recommended `jsx-a11y` rules as errors, so a click handler on an element that is not a control, a `role` without what it requires or a `<label>` without its control fail CI. A deliberate case keeps the rule and says why on the line: `// eslint-disable-next-line jsx-a11y/<rule> -- <reason>`, the reason being what the element is, not that the rule is wrong. **Every `<dialog>` has an accessible name**: `aria-labelledby` its heading, with the id from `useId` (never a fixed one, which a second instance on the page would repeat), or `aria-label` when it has no heading. Neither the linter nor axe sees it on the native element (axe's `aria-dialog-name` looks at `role="dialog"`), so `components/dialog-names.test.ts` parses every `<dialog>` of `app/` and `components/` and fails on the unnamed one. **Every popup of the platform is [`PlatformPopup`](/components/platform/shared/platform-popup)** (2026-10-06): the only fixed part is the strip at the top, the name by `title` and the cross; what is under it is the content's, which pads itself and brings its own fields and buttons, and picks its width by name (`sm`/`md`/`lg`); it has no trigger, the host opens and closes it through its `ref`. **Every destruction or cancellation goes through [`PlatformConfirmPopup`](/components/platform/shared/platform-confirm-popup)**, a different and heavier popup (no strip and no cross, a disc with the bin, the minus or the ban sign by verb — «Eliminar», «Quitar», «Cancelar» —, a danger rule along its top, a backdrop of its own, and the fields that have to be written first, such as the reason of a cancellation; with the verb «Cancelar» the way out says «Volver»), mounted as a SIBLING of the popup it is opened from and opened ON TOP of it, never a body that swaps itself for the question: on confirm it runs the action, closes itself and calls `onDone`, where the host closes the popup beneath; «Cancelar» and Escape close only the confirmation. No other file writes a `<dialog>` (`components/platform/popups.test.ts`).
- **What is drawn is checked by axe, story by story.** `npm run test:storybook` renders every story in a headless Chromium, in light and in dark, and fails the one where axe finds a violation in what its `play` leaves on screen — so a popup is checked only if a `play` opens it. A known failure is marked on that story, `parameters: { a11y: { test: "todo" } }` under a comment `// a11y: todo until <what fails> (<rule>)`, until its component is fixed; no rule is switched off for every story without a comment that says why ([Storybook](/ui/storybook#stories-as-tests)).
- Images always go through `next/image`; never a raw `<img>`. Remote images are limited to `res.cloudinary.com` (`next.config.ts`), and `lib/remote-image.ts` guards user-typed URLs before they reach `next/image`.
- **One action, one verb**: «Agregar» puts something into a set, «Quitar» takes it out of where it is without destroying it, «Eliminar» destroys it; «Añadir» and «Borrar» are not written. A hint or an error uses the verb of the button it is about, and a `pendingLabel` is a gerund with «…». The table is in the [Glossary](/glossary#verbs-of-the-interface), and `components/ui-verbs.test.ts` fails on a verb that lost.
- **Every shared piece of the platform has a story.** A piece of `components/platform/shared/` lives in a folder of its own beside `<name>.stories.tsx`, with one story per state that matters. In any stories file, the `title` is its path with the product first and the export name in place of the component's folder (`platform/shared/PlatformNotice`), every story has a JSDoc line (`/** … */`) that says what it shows, and its component's page in `docs/` names the file in a «Story» row right after «Stylesheet». Every story titled `platform/…`, `chess/…` or `icons/…` also has its tile on the [overview sheet](/ui/storybook#overview) (`platform/Overview`), which draws it with sample data and links to its Docs page. `components/stories.test.ts` holds the folder, the file, the title, the JSDoc, the row and the tile, on every stories file of the repository but the pages' (the overview, the foundations, the primitives and the icon gallery, which name the page); the states are a matter of review. `ImageUpload` is its one listed exception until its server action can be mocked. How to write one: [Storybook](/ui/storybook).
- Copy shown to users is **Spanish**, including URLs (`/estudios`, `/profesor/alumnos`). Dynamic segment names (`[courseId]`) stay in English because they are code identifiers and never appear in the address bar.
- **Every comment is written in English**, wherever it lives: code, CSS, tests, scripts, `prisma/schema.prisma`, workflows, `.env.example`, `.gitignore` and any other configuration file; like every other identifier. A comment that quotes a label, a URL parameter or a catalog value keeps it verbatim in Spanish, because that is the string in the product. The one exception is generated files: `payload-types.ts` reproduces the CMS field descriptions, which are copy, and is never edited by hand.
- `components/` mirrors the products in `app/`: `site/`, `platform/` and `auth/`. Inside each product, `sections/` holds the page sections (`.section.tsx`, with the `.comp.tsx` pieces only they use) and `shared/` the pieces several of that product's sections reuse; `chess/` (board, viewer, diagram) and `icons/` serve every product. There is no `common/` folder: a piece belongs to one product or to the chess domain.

## CSS

- **Strict BEM, Yandex flavour:** `block__element`, modifier `_key_value` (`platform-table__head_align_right`), boolean modifier `_open`.
- **One CSS file per component**, imported by that component, and **every rule nested under the root selector** with native CSS nesting (`&`). Media queries go inside the block. Nothing global except `globals.css`, `platform.css` and the intentional `.blog-button` helpers.
- **Desktop-first** media queries, and **only Tailwind's five breakpoints**: 640, 768, 1024, 1280 and 1536px, written in the range syntax — `@media (width < 1024px)` below one, `(width >= 1536px)` from one. A height is not a breakpoint and stays free. `components/platform/breakpoints.test.ts` holds it.
- Colours and spacing come from tokens: `--color-*` in `app/(frontend)/globals.css` (public site, plus board colours `--board-light`/`--board-dark`) and `--platform-*` in `app/(platform)/platform.css` (private area). A bare hex value in a component stylesheet is debt. The platform's and the access pages' stylesheets have none; the ones that remain are in the public site's stylesheets and in `components/chess`, where all but `EloTable`'s are the fallback of a `--platform-*` token (`var(--platform-surface, #2b2723)`) for the public site, where those tokens do not exist. No task tracks them.
- **The platform has two themes, and a colour is written as a pair.** Every `--platform-*` colour is declared with `light-dark(<light>, <dark>)` in the one `:root` block of `platform.css`; adding or correcting a colour means touching one line, and the two values are always read together. Which of the two applies is decided by `color-scheme` on `:root` — `light dark` by default, so the platform follows the machine, and `light`/`dark` when `:root[data-theme]` says the person chose (see [Themes](/architecture/themes)). **`color-scheme` must stay on the same element as the tokens**: Turbopack compiles `light-dark()` through Lightning CSS into helper variables declared wherever the `color-scheme` is, and declared one element below they never reach the tokens above them.
- **Filling in a form, focus and what is chosen are blue** (2026-10-06). The focus ring inside a `<form>` and on any field one types in, that field's border, a ticked box, a chosen card, a switch that is on and a chosen day use `--platform-selection` (with `-soft`, `-wash` and `--platform-on-selection`): in the light theme the accent is the same red as an error (`--platform-danger`), and a focused field read as an invalid one. The pieces that hold a value (`PlatformCheckbox`, `PlatformSwitch`, the cards) draw their blue ring themselves, also outside a `<form>`, and an invalid field keeps its red with the focus (border and ring `--platform-danger`). **Outside a form** — studying, moving around, reading one's progress — the focus ring is the accent's red (`--platform-accent-ink`), like the rest of the brand: the main buttons, the logo, the current lesson, an active tab or filter. See [Styling](/ui/styling) for the tokens.
- **A text reaches 4.5:1 on what it is written on, in both themes.** The subtle grey (`--platform-text-subtle`) is for the white surfaces only (`surface`, `surface-soft`); on a grey or tinted fill (`bg`, `surface-neutral`, `surface-sunken`, the accent's soft and wash) the text is `--platform-text-muted`. `components/platform/platform-tokens.test.ts` reads the stylesheets and fails on a colour that is not a pair, on a token that is used and not declared, on a text colour under the minimum on its fill, and on a rule that sets its own colour and fill as a pair `TEXT_PAIRS` (`lib/platform-tokens.ts`) does not list, so Storybook's «Text on a surface» page shows every pair a rule writes.
- **Font sizes and spaces come from the scales.** A `font-size` is one of the ten `--platform-type-*` tokens (12 to 52px) and a `gap`, `padding` or `margin` one of the twelve `--platform-space-*` (a 4px grid, 2 to 96px; a negative margin is `calc(-1 * var(…))`), never a px of its own. What stays in px: a 1px hairline, a px inside a `calc()` of geometry, and the board's coordinates (9px). The platform has no `zoom` since 2026-10-02: the steps carry the enlargement it gave, and from 1536px (`2xl`) every token takes a step up in one `@media` block of `platform.css`, which no stylesheet has to know about. The four chess stylesheets the public site also draws write each token with the site's size as its fallback. A `font-family` reads a `--platform-font*` token or inherits, the ELO table (drawn only on the site) aside. `components/platform/type-and-space.test.ts` holds it; the scales are drawn in Storybook and described in [Styling › Type and space](/ui/styling#type-and-space).
- **Whoever asks for less motion gets it everywhere.** A stylesheet that starts an animation stills it under `prefers-reduced-motion: reduce` (`animation: none`; cut to an instant, `animation-duration: 1ms`, when the component waits for `animationend`), and does the same with a `transition` that moves or resizes something (`transform`, a width, a height, a position; a colour that fades is not motion and is left to the hover rules of `globals.css`). The `reduce` block goes **after** the rule it answers: under `@media` a rule weighs what it weighs outside it, and of two that weigh the same the later one wins; `scroll-behavior: smooth` lives inside `prefers-reduced-motion: no-preference`; and code that passes `behavior: "smooth"` reads the preference with `matchMedia` first. `components/reduced-motion.test.ts` reads every stylesheet and component of both products and fails on the one that forgets.
- No Tailwind (it was removed), no CSS-in-JS, no CSS Modules.
- The full token list, the helper classes and worked examples are in [Styling & design tokens](/ui/styling).

## Data and authorisation

- The UI never imports Prisma or Payload. Pages call `services/<domain>/<domain>.service.ts`; the mapper returns the `*.types.ts` view model with labels and hrefs already built.
- Route hrefs come from `lib/platform-routes.ts` (`platformRoutes`, `teacherRoutes`, `staffRoutes`), never from template strings in components.
- Every platform page's **first `await`** is either a data service (which calls the DAL) or `getCurrentUser()` itself. Every `/profesor` page and action opens with `requireTeacher()`; every `/administracion` one with `requireStaff()`.
- A new route under `app/(platform)` must be added to `PROTECTED_PATH_PREFIXES` (`constants/platform/auth.const.ts`) **and** to the literal `matcher` in `proxy.ts`; `proxy.test.ts` fails if the two lists diverge, and also if a folder of `app/(platform)` is in neither.
- Restricted domains are catalog tables with a stable `code`. TypeScript mirrors them as `as const` objects in `constants/platform/*-codes.const.ts`; no TS enums, no Prisma enums.
- Lists with `@@unique([parent, order])` are reordered only through `services/shared/reorder.ts`.
- **Classes** (2026-10-14): a payment is a `ClassPayment` and a seat is the participation; what is left is derived on reading (`paymentSeats`), never stored, and a paid class never expires. A no-show spends the seat; attendance never moves money. «Gratis» (`isFree`) is not «Sin pago» (`paymentId` null), and «sin pago» is read only through `isUnpaidSeat`/`unpaidSeatWhere`. The student never sees an amount. Seats, attendance, status and schedule are written by `syncClassSeat`/`moveClassSeat`, `recordAttendance`, `transitionClassStatus` and `createClassRecord`/`syncClassSchedule`/`syncClassMeeting` in `services/shared/`, and the end and the meeting columns are computed only by `classScheduleColumns`/`classMeetingColumns` (`services/shared/class-writers.test.ts` reads every write of the app as TypeScript and `class-roles.test.ts` keeps the teacher's side away from the staff's writers); the seed writes the facts as data and the seats through their writers; every staff mark carries a reason and is kept in `ClassAttendanceChange`. The whole of it: [Classes](/platform/classes). **Who does what**: the staff creates, schedules, reschedules, cancels, changes the teacher and the link, adds and removes students, registers payments, gives free classes, changes attendance with a reason and gives a no-show's seat another date; the teacher only sees their assigned classes, gives them a topic and content by visibility, takes attendance, finalizes, changes their own marks and leaves the summary and the recording; the student sees their classes, their group classmates and their balance, never amounts. `class-roles.test.ts` keeps the frontier, with no exceptions.
- **Exercises** (2026-10-16): **one table, `Exercise`, holds every authored exercise** (a teacher's, the library's and, from phase 2, a lesson's, owned by the lesson); `TrainingExercise` stays only for the dormant trainer's derived line. The solution is a PGN played on the board (`[FEN]` + moves, variants and comments) and the source of everything else. Five writers in `services/shared/`, and nobody else writes their columns: `createExerciseRecord`/`syncExerciseSolution` (the solution, the kind, its N and the frozen columns, always through `...exerciseSolutionColumns(…)`), `transitionOwnExercise`/`reviewLibraryExercise` (the status and the review's stamps, by the table of `exercise-status-transitions.ts`) and `recordExerciseAttempt` (the attempt, its first mistake, the student's standing and the activity; `rebuildUserExerciseState` folds the same rule). **Every insert of an exercise goes through `createExerciseRecord`**, which creates it as a draft (the save, «Duplicar», the copy to a lesson and the import; a copy carries `exerciseCopyInput`'s whitelist); `services/shared/exercise-writers.test.ts` holds it. Who solves, picks, lists or watches what comes from one where-builder, `exercise-visibility-rules.ts`. The first wrong move decides the attempt (failed), and so does «Ver la solución»; only the author's lines are accepted, «Mate en N» included (another mate outside the tree is wrong). **One scored attempt per exercise per study day**: the rest of that day stores nothing, under `lockExerciseFamily`'s row lock; «Ejercicios superados» and the streak count each exercise once. A class block «Ejercicio» (phase 3, D29) holds one to ten exercises through `ClassBlockExercise`, written only by the teacher's block actions inside the block's transaction; the student solves them from the class, and the attempt keeps its `classBlockId`. All of it behind `EXERCISES_ENABLED`. The whole of it: [Exercises](/platform/exercises); the model: [Data model](/platform/data-model).
- A uniqueness conflict (`P2002`) is recognised only with `isUniqueConstraintError(error, "<index>", "<column>")` from `services/shared/prisma-errors.ts`, never with a hand-written `catch` that compares the code or reads `meta.target`: with the pg driver adapter `meta.target` is not there, and the `catch` lets a 500 out. The name has to be one of the error's names, not appear inside one. `services/shared/prisma-errors.test.ts` fails on a file that compares a code with `"P2002"` or reads `meta.target` outside the helper.

## Server actions

- `"use server"` modules export **async functions only**; messages and constants live in `constants/platform/*-messages.const.ts`.
- Read form fields through a zod schema with `parseForm` from `services/shared/form-schema.ts` (`formText`, `formOptionalText`, `formOptionalUrl`, `formInt`, `formLenientInt`, `formCheckbox`, `formEmail`, `formTextIfPresent`, `formReturnTo`, `readIds` for the hidden ids); the text helpers count a line break as one character, as a textarea's `maxLength` does, though a form sends it as CRLF, and what they return has LF line breaks; the schema is the action's contract, bounds every input and names the field that failed so the action answers with the code its page knows.
- Resolve the user first, then rate-limit with `allowAction(key, limit, windowMs)` (`lib/rate-limit.ts`), then validate, then write, then `revalidatePath`.
- **A form in a popup** (2026-10-15) uses `useActionState` with the states of `services/shared/form-state.ts`: the section on the server imports the action and passes it to the popup's host as a prop (no component with a story imports a `.actions.ts`; `components/stories-reach.test.ts` walks the stories' imports), the form is a `PlatformForm` with `action={formAction}`; when the action fails it returns the field errors and what was sent (`readFormValues`, never a password), so every field opens again with it after React resets the form (`defaultValue` from `state.values`, and the Radix controls under `savedValueKey`); when it goes well it returns `status: "done"` with the notice, a `useEffect` calls `onDone(notice)`, and the host closes the popup and replaces the address with `withNoticeParam`. The popup's content is remounted on each use: the host bumps its key in the popup's `onClose`, never in the click that opens. A confirmation and a page form redirect with `withNoticeParam` or `withErrorParam` instead.
- A success worth telling travels as `?aviso=<code>[.arg…]` (`withNoticeParam`, `services/shared/safe-return-to.ts`; the arguments are numbers or ids, never a name, and the helper throws on anything else); the page reads it with `readNotice` (`constants/platform/class-messages.const.ts`, where `CLASS_NOTICES` gives the text or leaves it to the page to compose with its own data) and draws it as a `PlatformNotice` with `variant="success"`; the shell takes it out of the address once drawn, like `?error=`. `safe-return-to.test.ts` fails on an `aviso=` written by hand.
- Errors travel back as a redirect to the page with `?error=<code>`, always built by `withErrorParam` (`services/shared/safe-return-to.ts`), which escapes the code and continues a query the path already carries; `services/shared/safe-return-to.test.ts` reads every `*.actions.ts` and fails on a `?error=` written by hand. The page translates the code with the message map. The only exceptions return state through `useActionState`: account creation and password reset, because a temporary password must never sit in a URL, the «Autores» dialog, which stays open over the page and has to get the outcome back itself, and the exercise editor (`ExerciseAuthoring`, 2026-10-16), which keeps its board and its fields in the browser: a refused save returns its errors, each mapped to its tab, and only a save that went through redirects with its notice. A result worth telling travels the same way as an error, in a parameter of its own: the PGN imports redirect with `?importadas=<stored>.<without moves>.<over the limit>` (`withImportReport`), and the page reads it back with `readImportReport`, which gives nothing for a value that could not have happened, because anybody can type a parameter. Both are said once: the platform's shell takes them out of the address as soon as the page has drawn them ([`ClearResultParams`](/components/platform/sections/shell/clear-result-params), with the list in `RESULT_PARAMS` of `lib/result-params.ts`), so the notice stays on screen until the next render of the page — the next action that revalidates, a reload — and that render no longer says it.

## Chess content

- The PGN is the content. Lessons, games and class blocks store PGN text; positions are derived at read time by `lib/chess`.
- A move inside a PGN tree is addressed by a **dotted path** of child indexes from the root (`"0.0.1.0"`). `TrainingExercise.path` and `ClassBlock.movePath` use it.
- Positions are identified by `createPositionHash(fen)` (`lib/chess/position-hash.ts`), computed on the server only.

## Play

- **Playing never counts toward the streak.** No module of `services/play`, `services/bots` or `services/profile` reaches the writer of `UserActivity`/`UserStatDaily`, nor names them; `services/play/no-activity.test.ts` walks their imports with `lib/testing/module-reach.ts`. A played game is a `PlayedGame`, never a study's `Game`; «Guardar en un estudio» makes a copy.
- **A bot is weakened only through UCI, on our side of the protocol**: `Skill Level`, `UCI_LimitStrength`/`UCI_Elo`, nodes or depth, and `pickBotMove`'s choice; never by time (`SearchBudget` takes no `movetime`; the project's one `movetime` is the analysis board's full-strength module, `FULL_STRENGTH_PROFILE`, never calibrated nor saved), with `ucinewgame` per game and `Hash 16` said out loud. The engine (`public/engine/`, GPL) is not modified. A label the calibration (`npm run bots:calibrate`) cannot reach moves in a new migration printed by `npm run bots:sql`, never by editing an old one ([Bots](/chess/bots)).
- **How a game ended is said in the player strips and under the board, never over it**: nothing covers the board ([Play](/platform/play)).

## Documentation and debt

- Debt you find but do not fix goes to `IMPROVEMENTS.md` with area, priority (low · medium · high · extreme) and how to approach it. Mechanical, well-specified tasks go to `TODOS.md`. Risks the project accepts knowingly go to `WARNINGS.md` with what, why and the way out. The three are in English and **local only**: gitignored, never in the remote, so a fresh clone does not have them.
- **Every important change is documented in the same commit**, not afterwards: behaviour, a convention, a route, the data model, a script, an environment variable, or a decision worth recording. Edit the page of this site that covers the area you touched, and rebuild it (`cd docs && npm run build`) when its pages changed.
- `README.md` stays the quick reference of the repository, in English; this site is the long-form documentation.
- Before touching framework APIs, read `node_modules/next/dist/docs/`: Next 16 renamed middleware to `proxy.ts`, made `params`/`searchParams` promises, changed caching APIs and more.

## Coding agents

`.claude/settings.json` is the repository's Claude Code policy. It only restricts — it holds no `allow` rule — and a `deny` or `ask` rule wins over an `allow` in any other settings file, so it holds whatever your own settings say.

**Never** (`deny`):

- Reading or editing `.env.local` and `.env`. They hold the database URLs (the managed ones on commented lines), `PAYLOAD_SECRET` and the Cloudinary keys: edit them by hand. Prisma, Next and `scripts/` keep reading them, because the rule covers Claude's own file tools and the shell commands it recognises, not the programs it runs.
- `prisma migrate reset` and `prisma db push`: both throw data away, and the schema only moves through migrations.
- `docker volume prune`, `docker system prune` and `dropdb`: the local databases live in the `postgres-data` volume.
- A forced push, in any spelling the rules know (`--force…`, `-f`, a `+` refspec, `--mirror`): it would rewrite the published history and deploy it. If one is ever needed, the owner runs it.
- `gh repo delete` and `npm publish`.

**Ask every time**, also in auto mode (`ask`):

- `git push` and `gh pr merge`: every push to `main` is a Production deployment ([release order](/operations/deployment#release-order)).
- `npm run db:deploy`, `db:seed`, `user:create`, `user:password` and `collections:by-chapter`, and `prisma migrate deploy`, `prisma db seed` and `prisma db execute`: they write to whichever database `.env.local` points at.
- `docker compose down -v` (and `npm run db:down -- -v`), `docker volume rm` and `pg_restore`: they throw away or overwrite a database.
- `npm run db:backup`: it writes to no database, but it reads all of one — accounts and password hashes — onto the disk.
- `git filter-branch`, `git filter-repo`, `git reset --hard` and `git clean`: rewritten history and discarded work.
- `gh repo edit` (it can change the repository's visibility), scheduling a job (`CronCreate`, `CronDelete`) and editing `.claude/settings.json` or `.claude/settings.local.json`.

**Ask when the database is not this machine** (a hook): the rules above see a command's text, not where it writes, and `npm run db:migrate`, `npm run dev` (Payload pushes its schema), `stats:rebuild`, `positions:index`, `prisma …` or a `tsx scripts/…` are harmless against the container and destructive against the managed database. So the policy registers a `PreToolUse` hook on Bash, `.claude/hooks/database-target-guard.mjs`: for a command that uses the databases `.env.local` names, it reads `PLATFORM_DATABASE_URL` and `DATABASE_URI` the way dotenv does (the environment, then `.env.local`, then `.env`) and answers "ask" when either is not localhost — naming the variable, never the host or the URL. A command that touches no database gets no answer and goes on as before. It fails closed: an input or a file it cannot read gets "ask", and it is launched as `node … || exit 2`, so a hook that cannot start blocks the call. `agent-policy.test.ts` reads `.claude/settings.json` as Claude Code would (an invalid file is skipped whole, deny rules included), holds its main rules and runs the hook against a local and a managed folder.

It also sets `disableBypassPermissionsMode`, so no session can skip the prompts, and turns Claude's attribution off (`"attribution": { "commit": "", "pr": "", "sessionUrl": false }`): no `Co-Authored-By` trailer on a commit, no "Generated with" line or session link on a pull request.

- Your own `allow` rules and your `defaultMode` go in `.claude/settings.local.json`, which git ignores. What auto mode should know about the environment (this repository is public; a push to `main` deploys Production) goes in your user settings, under `autoMode.environment` in `~/.claude/settings.json`: Claude Code never reads `autoMode` from a repository.
- The policy applies to sessions started at the repository root, where `.claude/` lives.
- An agent started with worktree isolation (or a `--worktree` session) works in a full checkout under `.claude/worktrees/`. `.gitignore` (which Prettier reads), the ESLint ignores, `tsconfig.json` and `vitest.config.mts` all leave that folder out, so the four checks of the main checkout never read another checkout's files.
- **`.mcp.json` offers one MCP server, Next's own for development** (`next-devtools-mcp`, the one Next's bundled guide `node_modules/next/dist/docs/01-app/02-guides/mcp.md` describes). With `npm run dev` running it finds the dev server (`nextjs_index`) and calls the tools that server exposes at `/_next/mcp` (`nextjs_call`): the errors of the page that is open, the routes, a server action by its id, whether a route compiles — without the `next build` that needs both databases. It also answers from the docs bundled with the installed Next (`nextjs_docs`). It is pinned to an exact version on purpose — the guide's `@latest` would run whatever is published that day — and Claude Code asks each person before using it: the approval is personal and lives in `.claude/settings.local.json`, never in the committed policy.
- **On GitHub, two rulesets guard `main`**: no force push and no deletion, for everyone and with no exception (the last brake if a forced push slips past the rules here), and a green CI (`verify`) to land on it, which the admins bypass so the owner's direct pushes keep working ([Release order](/operations/deployment#release-order)).
- The rules match the command as it is written. `git -C . push`, `bash -c '…'` or a program that opens `.env.local` by itself are not stopped, so the policy brakes the usual path; it is not a sandbox.

## Definition of done

```bash
npm run format:check && npm run lint && npm run typecheck && npm test \
  && npm run storybook:build && npm run test:storybook
```

The same six checks CI runs, in the same order: the first that fails stops the job, so a file that drifted from Prettier hides every later result (`npm run format` fixes what `format:check` reports). The last renders every story in Chromium under axe and needs Playwright's browser once on each machine (`npx playwright install chromium`). Plus the documentation of whatever you touched, updated in the same commit, and `cd docs && npm run build` when its pages changed. Performance work is measured with Lighthouse against `npm run build && npm run start`, three runs, median.
