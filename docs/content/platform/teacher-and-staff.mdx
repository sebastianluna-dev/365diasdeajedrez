# Teacher & staff panels

Both panels are ordinary platform pages with a stricter border: `requireTeacher()` / `requireStaff()` as the first `await`, ownership inside every `where`, and guards before writes. Error codes map to `TEACHER_ERROR_MESSAGES` and `STAFF_ERROR_MESSAGES` in `constants/platform/`.

## Teacher panel — `/profesor`

### Dashboard

`services/teacher/teacher.service.ts` → `getTeacherDashboard()`: today's classes, the next 7 days, classes that still need attendance marked, and the number of actively assigned students. `getTeacherProfile()` and `updateTeacherProfile` (`teacher.actions.ts`) manage display name, title, bio (≤ 1000 chars), photo and IANA timezone (`constants/platform/timezones.const.ts`).

### Students — `/profesor/alumnos`

`services/teacher-students/`: only students with an **active** `TeacherStudent` row, and that condition is always inside the `where`. `getAssignedStudents(query?)`, `getAssignedStudentDetail(studentId)` (course progress, recent activity, shared classes), `getStudentStudy` and `getStudentGame` for the **read-only** view of a student's studies. Opening the study of an unassigned student by URL returns nothing, so the page 404s without revealing a name.

### Classes — `/profesor/clases`

`services/teacher-classes/`:

- `createClass`, `updateClassMeta` (title, description, `scheduledAt` typed in the teacher's zone and stored in UTC through `lib/timezone.ts`, duration 15–480 min, meeting provider and URL, visibility instant, recording URL, summary).
- `setClassStatus` obeys `class-status-transitions.ts`: `SCHEDULED → LIVE | COMPLETED | CANCELLED`, `LIVE → COMPLETED | CANCELLED`; completed and cancelled are final. Cancelling **is** deleting; there is no physical delete.
- Participants: `addParticipant` (must be an assigned student), `removeParticipant` (blocked if the student attended or has a payment), `markAttendance` (records `CLASS_ATTENDED` activity).
- Blocks: `addClassBlock`, `updateClassBlock`, `deleteClassBlock`, `moveClassBlock` (through `services/shared/reorder.ts`). Kinds: text, video (http(s) URL), game reference (a game from the teacher's own studies or an assigned student's, checked by `assertTeacherCanReferenceGame` at insert time; later reassignments do not break past classes), lesson reference, position reference (teacher's saved diagrams), or a game **transcribed in the block** (`ClassBlock.pgn`, edited on the analysis board). `movePath` captures "this position" from the viewer via `onPathChange`; `isMovePathBroken` flags paths that no longer resolve.
- `fetchReferencePgn` lets the block editor preview a referenced game or lesson; `listReferenceableGames` groups the games by study and marks the teacher's own.
- The teacher always sees `meetingUrl`; hiding it before `meetingUrlVisibleFrom` is a student-side rule.

## Staff panel — `/administracion`

### Dashboard

`services/staff/staff.service.ts` → counts of students (accounts that are neither teacher nor staff), active/inactive teachers, courses by status, classes in the next 7 days, and the actionable list of **students without a teacher**.

### Students (accounts) — `/administracion/alumnos`

`services/staff-students/`: staff sees every account but never its private content (no studies, no games). `createStudentAccount` (email + display name → account and default study in one transaction, with a password typed by staff or a generated temporary one, shown once), `resetStudentPassword` (new temporary password, all sessions destroyed), `updateStudent`. The detail shows the assignment history.

### Teachers and assignments — `/administracion/profesores`

`services/staff-teachers/`: `createTeacher` links an existing account (`listLinkableUsers`), `updateTeacher`, `setTeacherActive` (never delete), `assignStudent` and `endAssignment`. `assignment-rules.ts` plans a reassignment (close active rows, create a new one, or no-op if already assigned to that teacher); the partial unique index `teacher_student_one_active` is the final arbiter and its P2002 is caught by name.

### Courses — `/administracion/cursos`

`services/staff-courses/` is the content editor:

- Course: `createCourse` (name, slug and at least one content type, from the «Nuevo curso» dialog), `updateCourse` (name, slug — in the editor it is rewritten from the name whenever the name changes, and can be adjusted before saving; it is the address of the course's information page, `/cursos/<slug>`, so one that page would never answer to is refused as `invalid`: `explorar`, or eight digits, which are read as a course id (`isReservedCourseSlug`) —, description, content types — at least one, `contentTypeRequired` otherwise —, levels by slug (several or none)), `updateCourseCover` and `updateCourseThumbnail` (the course's two images — the wide 21:9 and the square 1:1 —, each stored the moment `ImageUpload` finishes uploading it from the browser with a signed Cloudinary request, or emptied when it is taken away; it answers `{ ok }` instead of redirecting, accepts only an image `next/image` can render, and `withCoverCrop` has rewritten the URL to `c_fill,ar_21:9,g_auto`. It is not part of `updateCourse`, so saving the metadata never touches the cover. Both read the previous URL before writing and delete from Cloudinary the file that stops being pointed at, as `updateAuthor` does with a photo), `publishCourse` (requires at least one chapter with a lesson that has PGN), `archiveCourse`, delete only while draft and without progress.
- A course record is three pages, which are its tabs: `/administracion/cursos/[courseId]` (metadata, images, authors, sources), `…/temario` (its chapters) and `…/partidas` (its games). A chapter's is three too: the chapter, `…/lecciones` and `…/partidas`. The syllabus and the lessons have a page of their own because the list is rows, and rows want the whole width. The three pages of each record live in a `(ficha)` route group whose **layout** draws the name, the status and the tabs — so they cannot drift apart and the header does not blink between them —; what hangs from the record (a lesson, a game on the board) is outside the group. The tabs are built in one place (`courseTabs`, `chapterTabs` in `staff-tabs.const.ts`), and which one is current is read from the address, because a layout is not told the path.
- The actions of a list come back to the page that draws it: the chapter ones to `…/temario` and the lesson ones to `…/lecciones`, with `?error=`, and they revalidate the record as a layout so the three pages and the counts of the tabs follow.
- Chapters: `createChapter`, `updateChapter` (name, description and `isPriority`, the mark that makes the whole chapter priority; role intro/closing enforced by the unique index), `reorderChapters`, `deleteChapter`. **A chapter's duration is not typed**: it is the sum of its lessons' minutes, cached on `Chapter.estimatedDuration` by `syncChapterDuration` in the transaction of the lesson write that moved it, so showing it never reads the lessons (2026-09-30). The panel says so under the figure.
- Chapter collection (`…/capitulos/[chapterId]/partidas`): `importChapterGames` pastes PGN into the chapter's `GameDatabase` (created on demand) using the same `pgn-import` and indexing as students, and comes back with the same `?importadas=` result the page turns into a notice; `deleteChapterGame` refuses if a lesson uses the game; `reorderChapterGames` writes the collection's order from the board screen's list, taking the whole list at once (`Game.order` is only indexed, so it does not need `services/shared/reorder.ts`, which exists for the orders that are unique per parent).
- A game on the board (`…/capitulos/[chapterId]/partidas/[gameId]`): `getChapterGame` reads it with its lessons and the chapter's other games, and two actions write it. `autosaveChapterGamePgn` saves the PGN as it is annotated and reindexes its positions; when the MOVES changed (`sameMoves`, not a comment nor an arrow) it stamps `pgnUpdatedAt` on every lesson that uses the game and remakes their derived exercise, in the same transaction, and refuses the save (`training`) if a trainable lesson would be left without a line. `updateChapterGameDetails` saves the record and writes it into the PGN's headers. The record's schema and that writing are `services/shared/game-record`, the same module the student's studies use: what a record is does not depend on who saved it.
- Lessons: `createLesson`, `updateLesson` (name, description, order, priority, role, estimated minutes, orientation, topics, `isTrainable`, training colour, own PGN), `setLessonGame` (link/unlink a game of the chapter's collection; the game's PGN becomes the content), `deleteLesson`, `reorderLessons`, `fileLessonPgnAsGame` (files a lesson's own PGN as a game of its chapter's collection and links it — the per-lesson version of `collections:by-chapter`, for content that no board could otherwise reach). Saving the PGN or toggling trainable calls `syncLessonTrainingExercise` so the **derived** exercise follows the mainline (`extractMainline`, `deriveExerciseData`); the action rejects a mainline with an illegal move or a colour with no moves to train. Creating, saving and deleting a lesson also call `syncChapterDuration`, in the same transaction and by the same shared-helper pattern, so the chapter's minutes follow — and a save that is refused takes the figure back with it.
- Exercises: `createExercise`, `updateExercise`, `deleteExercise`, `moveExercise` with the `ExerciseMovePicker` (moves are chosen on a board, never typed).
- Authors: `createAuthor` and `updateAuthor` from the «Autores» dialog (`AuthorsManager`) of the catalog and of the course editor — authors have no page of their own —. They take name, biography and photo and **return** their outcome (`AuthorFormState`, through `useActionState`) instead of redirecting, because the dialog stays open; the slug is never typed: `authorSlugFor` takes it from the name, with a number behind when another author has it, and an author who keeps their name keeps their slug. `manageCourseAuthors` adds an author to a course (`add`, after the last one), changes their role (`role`) or takes them out (`remove`), from the course's card (`CourseAuthors`); there is no reordering.
- Catalog readers for forms: `listContentTypes` (with `shortLabel` and `description`), `listLevels` (slug, name and the Elo range already worded; the levels in use, the easiest first), `listCourseStatuses`, `listTopics`, `listExerciseModes`, `listAuthorRoles`. Checkbox groups over a catalog (content types, levels, a lesson's topics) are written with `syncCatalogJoin` (`services/shared/catalog-join.service.ts`), which replaces the whole join set inside the caller's transaction; for the levels it matches the catalog by `slug` (`catalogKey`), which is what that catalog goes by.

### Sources of a course

`services/staff-sources/`: «Procedencia del recurso», where a course's material comes from. The sources are edited in the card of that name in the course editor's narrow column (`CourseSources`): `saveCourseSource(courseId, formData)` creates one (with `order = nextOrder(count)`) or, with a hidden `sourceId`, rewrites it, scoped to the course (`sourceMissing` otherwise); only `sourceTypeCode` is required — title, authors (free text), URL, year (1400–2100), edition, specific reference and staff-only notes are optional. `deleteCourseSource` removes one, from the source's own dialog. `getCourseAdminDetail` returns them in order, and the student's `getCourseById` returns the same rows without the notes. The one catalog reader is `listSourceTypes`.

There are no source entities any more: the page `/administracion/entidades` and the field of the form that cited one (the publisher of a book, the platform of a digital course) were taken out on 2026-09-27.

### Classes (support) — `/administracion/clases`

`services/staff-classes/`: global read view with filters (teacher, status, date range, text), payment data included, but exactly **two** actions: `setRecordingUrl` and `cancelClassAsStaff`. Blocks, attendance, participants and metadata belong to the teacher so that no two roles edit the same thing.

## Forms

Panels are Server Components with plain `<form action={serverAction}>` elements; the only `useActionState` forms are account creation, password reset and the author form of the «Autores» dialog. Tables use `PlatformTable` (semantic `<table>`, filters via search params). Uploading a cover uses `components/platform/shared/image-upload.comp.tsx`: it checks type and size in the browser (`constants/platform/upload.const.ts`, 1 MB since 2026-09-28, jpg/png/webp/avif), asks `createUploadSignature()` (staff only, 60 signatures per minute), posts the file straight to Cloudinary with the signed `folder`, `timestamp` and `allowed_formats`, and stores it at once with `updateCourseCover`. The size is a browser check alone: Cloudinary's upload API takes no maximum per request, so three covers of about 2 MB uploaded before that day are still stored and still work.
