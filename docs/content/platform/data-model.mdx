# Data model

`prisma/schema.prisma` describes the platform database. Prisma 7 setup:

- generator `prisma-client` with `output = "../lib/platform-db/generated"` (git-ignored; `npm run db:generate`);
- no `url` in the datasource: the CLI reads it from `prisma.config.ts` (`schema`, `migrations.path`, `migrations.seed = "tsx prisma/seed.ts"`, `datasource.url = PLATFORM_DATABASE_URL`), the runtime from `@prisma/adapter-pg` in `lib/platform-db/get-platform-db.ts`;
- `prisma.config.ts` loads `.env.local` and then `.env`.

## Design decisions

- **PGN is the content.** `Lesson.pgn`, `Game.pgn` and `ClassBlock.pgn` hold the chess material; there are no per-move tables. Positions, lines and diagrams are derived by `lib/chess` at read or index time.
- **Catalogs instead of enums.** Every restricted domain is a table with `id`, `code` (unique, stable), `label` (Spanish), `order` and sometimes `isActive`. Business logic compares `code`; the seed upserts them; TypeScript mirrors them in `constants/platform/*-codes.const.ts`.
- **Composite primary keys** for progress and join tables.
- **Roles by row existence** (`Teacher`, `Staff`).
- Constraints Prisma cannot express are written by hand in the migrations (below).

## Catalogs

`CourseType` (OPENING, ENDGAME, STRATEGY, TACTICS) · `CourseStatus` (DRAFT, PUBLISHED, ARCHIVED) · `AuthorRole` (CONTENT_AUTHOR, DIGITAL_ADAPTATION) · `ContentRole` (INTRO, CLOSING) · `Level` (BEGINNER…EXPERT) · `BoardOrientation` (WHITE, BLACK, AUTO — AUTO only for user settings) · `ExerciseMode` (REPRODUCE_LINE, FIND_MOVE) · `ProgressStatus` (NOT_STARTED, IN_PROGRESS, COMPLETED) · `AttemptResult` (PASSED, FAILED) · `AttemptContext` (LESSON, CHAPTER_QUIZ, TRAINER) · `OwnerType` (USER, COURSE, TEACHER) · `DatabaseKind` (MY_GAMES, TOURNAMENT, STUDY, COLLECTION) · `GameSource` (MANUAL, PGN_IMPORT, PLATFORM_GAME) · `GameResult` (WHITE_WINS, BLACK_WINS, DRAW, ONGOING; the label is the PGN token) · `ClassStatus` (SCHEDULED, LIVE, COMPLETED, CANCELLED) · `MeetingProvider` (ZOOM, MEET, OTHER) · `ClassBlockKind` (TEXT, VIDEO, GAME_REF, LESSON_REF, POSITION_REF, FILE) · `TranscriptStatus` (PENDING, READY, FAILED) · `ActivityType`, `SubjectType`, `StatMetric` (see Activity) · `Topic` (hierarchical via `parentId`: TACTICS, OPENING_LINE, PAWN_STRUCTURE, ENDGAME, STRATEGY…).

Adding a value to a catalog is a seed row, not a migration.

## Content: Course → Chapter → Lesson

| --- | --- | --- |
| `Course` | `id` (8-digit numeric string, app-generated), `name`, `slug` (unique), `description`, `cover` (Cloudinary URL), `typeId`, `statusId`, `publishedAt` | Relations: chapters, `CourseAuthor` (with `AuthorRole`, ordered), `CourseLevel`, progress, settings, game databases, positions. |
| `Author` | `name`, `slug`, `bio`, `photo` | Course authors, managed by staff. |
| `Chapter` | `courseId`, `name`, `order`, `roleId?` (INTRO/CLOSING), `estimatedDuration` | `@@unique([courseId, order])`, `@@unique([courseId, roleId])` (at most one intro and one closing; normal chapters have `NULL`). One game collection per chapter. |
| `Lesson` | `id` (8-digit numeric), `chapterId`, `name`, `order`, `isPriority`, `roleId?`, `estimatedDuration`, `orientationId`, `gameId?`, `pgn`, `pgnUpdatedAt`, `isTrainable`, `trainingColorId?` | **Content source:** when `gameId` is set the lesson's content is that game's PGN (fixing the game fixes every lesson using it); otherwise `pgn`. Only `lessonPgnOf()` (`services/shared/lesson-pgn.ts`) decides. `onDelete: SetNull` on the game keeps the lesson alive without content. `@@unique([chapterId, order])`, `@@unique([chapterId, roleId])`. |
| `TrainingExercise` | `lessonId`, `order`, `modeId`, `path` (dotted), `startPly`, `endPly`, `startFen`, `line` (SAN, space-separated), `frozenAt`, `promptText`, `isDerived` | A **frozen copy** of a trainable segment so the trainer does not depend on parsing. | `LessonTopic` | `(lessonId, topicId)` | Topics feed the stats breakdown. |

## Studies: game databases and games

| Model | Key fields | Notes |
| --- | --- | --- |
| `GameDatabase` | `id` (nanoid 8), `ownerTypeId`, `userId?`, `courseId?`, `chapterId?`, `name`, `description`, `kindId`, `isDefault`, `order` | One table, two owners: a **user** (private studies) or a **course** (published material). | `StudyShare` | `databaseId`, `userId`, `teacherId?` | A **collection** handed to a student: read-only by ownership, not by this table. `@@unique([databaseId, userId])`. |
| `Position` | `ownerTypeId`, `userId?`, `courseId?`, `title`, `fen`, `orientationId`, `arrows` (json), `highlights` (json) | Saved diagrams reusable in class blocks. |

## Constraints written by hand

The initial migration and later ones add what Prisma cannot express:

```sql
-- exactly one owner
ALTER TABLE "GameDatabase" ADD CONSTRAINT ... CHECK (("userId" IS NOT NULL) <> ("courseId" IS NOT NULL));
ALTER TABLE "Position"     ADD CONSTRAINT ... CHECK (("userId" IS NOT NULL) <> ("courseId" IS NOT NULL));
-- at most one reference per class block
ALTER TABLE "ClassBlock" ADD CONSTRAINT ... CHECK ((("gameId" IS NOT NULL)::int + ("lessonId" IS NOT NULL)::int + ("positionId" IS NOT NULL)::int) <= 1);
-- NULL topic must not duplicate rows
CREATE UNIQUE INDEX ... ON "UserStatDaily"("userId", "day", "metricId", "topicId") NULLS NOT DISTINCT;
-- one active teacher per student
CREATE UNIQUE INDEX "teacher_student_one_active" ON "TeacherStudent" ("studentId") WHERE "endedAt" IS NULL;
-- one default study per user (migration 20260904190000)
CREATE UNIQUE INDEX "game_database_one_default_per_user" ...
```

Rules that need more than one table (owner type ↔ populated column, block kind ↔ populated field) are validated in the services.

## Migrations

`prisma/migrations/` (2026-08-30 → 2026-09-09): `init`, `add_exercise_frozen_at`, `add_auth_sessions`, `add_teacher_staff_panels`, `add_game_positions`, `add_game_title`, `shorten_study_and_game_ids`, `chapter_slug_and_short_lesson_ids`, `numeric_student_ids`, `lesson_training`, `derived_exercise_flag`, `lesson_training_color`, `class_block_pgn`, `game_order`, `game_player_details`, `rate_limit`, `study_types_and_shares`, `daily_goal`, `lesson_game_reference`, `chapter_collections`, `simplify_lesson_metadata`, `content_roles`, `composite_indexes`.

Workflow:

1. Edit `schema.prisma`, run `npm run db:migrate` (creates and applies a migration in development) or write the SQL by hand when the change needs a CHECK, a partial index or data movement. For index-only changes `npx prisma migrate diff --from-schema-datamodel <old> --to-schema-datamodel <new> --script` produces the SQL.
2. `npm run db:generate`, then `npm run typecheck`.
3. Production: back up first (`pg_dump`), then `npm run db:deploy`. Migrations have no down path.
4. If the change needs data movement that SQL cannot do (reading PGN headers, for instance), write a script like `scripts/migrate-chapter-collections.ts`: short transactions, idempotent, resumable, with a `--dry` mode.

## Seed

`prisma/seed.ts` + `prisma/seed-data.ts`: idempotent (catalogs by `upsert(code)`, domain rows by fixed ids or natural keys), creates the three demo accounts, a course with chapters/lessons/exercises, studies and games (indexed with `indexGamePositions`), classes with blocks and a transcript, activities and rebuilt daily stats. `SEED_NOW` pins the reference instant. See [Scripts & seed](/operations/scripts-and-seed).
