# Data model

`prisma/schema.prisma` describes the platform database. Prisma 7 setup:

- generator `prisma-client` with `output = "../lib/platform-db/generated"` (git-ignored; `npm run db:generate`) and `previewFeatures = ["relationJoins"]`, which makes `relationLoadStrategy: "join"` the default of every read (see [Data access](/architecture/data-access));
- no `url` in the datasource: the CLI reads it from `prisma.config.ts` (`schema`, `migrations.path`, `migrations.seed = "tsx prisma/seed.ts"`, `datasource.url = PLATFORM_DATABASE_URL`), the runtime from `@prisma/adapter-pg` in `lib/platform-db/get-platform-db.ts`;
- `prisma.config.ts` loads `.env.local` and then `.env`.

## Design decisions

- **PGN is the content.** `Lesson.pgn`, `Game.pgn` and `ClassBlock.pgn` hold the chess material; there are no per-move tables. Positions, lines and diagrams are derived by `lib/chess` at read or index time.
- **Catalogs instead of enums.** Every restricted domain is a table with `id`, `code` (unique, stable), `label` (Spanish), `order` and sometimes `isActive`. Business logic compares `code`; the seed upserts them; TypeScript mirrors them in `constants/platform/*-codes.const.ts`. `Level` is identified by a `slug` instead, which is what the course list is filtered by; no logic compares against its rows.
- **Composite primary keys** for progress and join tables.
- **Roles by row existence** (`Teacher`, `Staff`).
- Constraints Prisma cannot express are written by hand in the migrations (below).

### `Level`: the catalog that goes by slug

Who a course is aimed at. A fixed catalog like the others: six rows that the migration creates and the seed keeps, not edited from the interface (a page for it, `/administracion/niveles`, existed for a day and was taken out on 2026-09-27). Its rows carry more than a label:

| Field         | Meaning                                                                                                                                               |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `slug`        | Unique; what `/cursos?nivel=` and the course form carry.                                                                                              |
| `name`        | «Iniciación», «Principiante», «Intermedio», «Avanzado», «Experto», «Maestro».                                                                         |
| `description` | What is worked on at that level.                                                                                                                      |
| `order`       | Position by difficulty, the easiest first. Ties are broken by `eloMin` and by name.                                                                   |
| `eloMin`      | Inclusive lower end, never negative. «Iniciación» is `0`.                                                                                             |
| `eloMax`      | Inclusive upper end; `null` = no upper bound («Maestro»: `2200`, `null`).                                                                             |
| `isActive`    | `false` hides a level from the student, from the filter and from the course editor; its `CourseLevel` rows stay. Nothing in the interface changes it. |

The platform ships with 0–799, 800–1199, 1200–1599, 1600–1999, 2000–2199 and 2200+. Three decisions are part of the model:

- **The ranges are orientative.** They are an internal classification, not official categories nor equivalences between FIDE, Chess.com and Lichess, and «Maestro» names the difficulty of the content, not a title. Every screen the student sees a range on says «El Elo es orientativo».
- **Nothing is restricted by Elo.** No read nor action compares a range with anything: `publishedCourseWhere` is still the only condition to open a course.
- **No rating of the student is stored**, so a missing rating cannot become a zero. A player without a rating belongs to whatever level their knowledge says. If a rating is ever added to `User`, it has to be nullable.

Levels are apart from the content types (what the course teaches) and from the sources (where its material comes from): three different tables, three different joins.

Adding a value to a catalog is a seed row, not a migration. Replacing a catalog is one: `content_types` (2026-09-27) turned the single `CourseType` of each course into rows of `CourseContentType` (OPENING → OPENINGS, ENDGAME → ENDGAMES) and dropped the old table. `editable_levels` (2026-09-27) updated the four rows of `Level` **in place** (`BEGINNER` → `principiante`…; «Experto» became 2000–2199), so their ids and every `CourseLevel` assignment survived, and inserted «Iniciación» and «Maestro» with `ON CONFLICT ("slug") DO NOTHING`, so nothing is duplicated.

## Exercises

The bank of authored exercises (migrations `20261016120000_exercises` and `20261016130000_lesson_exercises`): one table, `Exercise`, holds a teacher's exercises, the academy's library and, since phase 2, a lesson's exercises (`lessonId` set: the lesson owns it, D04, D05, D41; never in a bank, a series or the library). An exercise is a starting position and a solution played on the board, with variants and comments, kept as a PGN; the student plays their moves and the platform answers until the line ends. Its attempts are `TrainingAttempt` rows with `exerciseId` (above). The single writers it names live in `services/shared/`, and the schema comment of each derived column names its one writer. The rules the model serves — how an exercise is solved, how an attempt is recorded, who sees what — are in [Exercises](/platform/exercises).

## Played games («Jugar»)

## Constraints written by hand

The initial migration and later ones add what Prisma cannot express:

```sql
-- exactly one owner
ALTER TABLE "GameDatabase" ADD CONSTRAINT ... CHECK (("userId" IS NOT NULL) <> ("courseId" IS NOT NULL));
ALTER TABLE "Position"     ADD CONSTRAINT ... CHECK (("userId" IS NOT NULL) <> ("courseId" IS NOT NULL));
-- at most one reference per class block
ALTER TABLE "ClassBlock" ADD CONSTRAINT ... CHECK ((("gameId" IS NOT NULL)::int + ("lessonId" IS NOT NULL)::int + ("positionId" IS NOT NULL)::int) <= 1);
-- NULL topic must not duplicate rows
CREATE UNIQUE INDEX ... ON "UserStatDaily"("userId", "day", "metricId", "topicId") NULLS NOT DISTINCT;
-- one active teacher per student
CREATE UNIQUE INDEX "teacher_student_one_active" ON "TeacherStudent" ("studentId") WHERE "endedAt" IS NULL;
-- a user name is 3–30 lower-case letters, digits and single dashes (migration 20261008120000)
ALTER TABLE "User" ADD CONSTRAINT "user_slug_format" CHECK ("slug" ~ '^[a-z0-9]+(-[a-z0-9]+)*$' AND char_length("slug") BETWEEN 3 AND 30);
-- «Jugar» (migration 20261008130000): a bot's label, a seat is a person or a bot,
-- a closed game says how, a game against a bot is never rated
ALTER TABLE "Bot" ADD CONSTRAINT "bot_elo_range" CHECK ("elo" BETWEEN 400 AND 2800);
ALTER TABLE "PlayedGame" ADD CONSTRAINT "played_game_white_one_seat" CHECK (("whiteUserId" IS NULL) <> ("whiteBotId" IS NULL));
ALTER TABLE "PlayedGame" ADD CONSTRAINT "played_game_black_one_seat" CHECK (("blackUserId" IS NULL) <> ("blackBotId" IS NULL));
ALTER TABLE "PlayedGame" ADD CONSTRAINT "played_game_closed_has_termination" CHECK (("finishedAt" IS NULL) = ("terminationId" IS NULL));
ALTER TABLE "PlayedGame" ADD CONSTRAINT "played_game_bot_never_rated" CHECK (NOT ("isRated" AND ("whiteBotId" IS NOT NULL OR "blackBotId" IS NOT NULL)));
-- one open game against a bot per person and colour (games between people have no cap)
CREATE UNIQUE INDEX "played_game_white_user_open_vs_bot" ON "PlayedGame"("whiteUserId") WHERE "finishedAt" IS NULL AND "blackBotId" IS NOT NULL;
CREATE UNIQUE INDEX "played_game_black_user_open_vs_bot" ON "PlayedGame"("blackUserId") WHERE "finishedAt" IS NULL AND "whiteBotId" IS NOT NULL;
-- one default study per user (migration 20260904190000)
CREATE UNIQUE INDEX "game_database_one_default_per_user" ...
-- a level's Elo range is never negative nor upside down (migration 20260927140000)
ALTER TABLE "Level" ADD CONSTRAINT "level_elo_range" CHECK ("eloMin" >= 0 AND ("eloMax" IS NULL OR "eloMax" >= "eloMin"));
-- classes (migration 20261014120000): a payment is positive and buys 1–50 classes; a class lasts,
-- a group seats 2–12, its end is its start plus its duration; a free seat has no payment; only a
-- no-show's seat is moved (IS FALSE, not = false: a null mark would pass)
ALTER TABLE "ClassPayment" ADD CONSTRAINT "class_payment_amount_positive" CHECK ("amount" > 0);
ALTER TABLE "ClassPayment" ADD CONSTRAINT "class_payment_class_count_range" CHECK ("classCount" BETWEEN 1 AND 50);
ALTER TABLE "Class" ADD CONSTRAINT "class_capacity_range" CHECK ("capacity" IS NULL OR "capacity" BETWEEN 2 AND 12);
ALTER TABLE "Class" ADD CONSTRAINT "class_duration_positive" CHECK ("durationMin" > 0);
ALTER TABLE "Class" ADD CONSTRAINT "class_ends_at_derived" CHECK ("endsAt" = "scheduledAt" + make_interval(mins => "durationMin"));
ALTER TABLE "ClassParticipant" ADD CONSTRAINT "class_participant_free_has_no_payment" CHECK (NOT ("isFree" AND "paymentId" IS NOT NULL));
ALTER TABLE "ClassParticipant" ADD CONSTRAINT "class_participant_moved_was_absent" CHECK ("seatMovedAt" IS NULL OR "attended" IS FALSE);
-- exercises (migration 20261016120000): an Elo-like difficulty, «Mate en N» up to 5, at most three
-- hints, a plausible source year, a teacher's series never in the library, and an attempt at
-- exactly one exercise (the line drill or an Exercise)
ALTER TABLE "Exercise" ADD CONSTRAINT "exercise_difficulty_range" CHECK ("difficulty" BETWEEN 400 AND 3000);
ALTER TABLE "Exercise" ADD CONSTRAINT "exercise_mate_in_range" CHECK ("mateIn" IS NULL OR "mateIn" BETWEEN 1 AND 5);
ALTER TABLE "Exercise" ADD CONSTRAINT "exercise_hints_max" CHECK (cardinality("hints") <= 3);
ALTER TABLE "Exercise" ADD CONSTRAINT "exercise_source_year" CHECK ("sourceYear" IS NULL OR "sourceYear" BETWEEN 1400 AND 2100);
ALTER TABLE "ExerciseSeries" ADD CONSTRAINT "exercise_series_library_published" CHECK ("teacherId" IS NULL OR "publishedAt" IS NULL);
ALTER TABLE "TrainingAttempt" ADD CONSTRAINT "training_attempt_one_exercise" CHECK (("trainingExerciseId" IS NULL) <> ("exerciseId" IS NULL));
-- lesson exercises (migration 20261016130000): one owner at most, and an order only inside a lesson
ALTER TABLE "Exercise" ADD CONSTRAINT "exercise_single_owner" CHECK (NOT ("teacherId" IS NOT NULL AND "lessonId" IS NOT NULL));
ALTER TABLE "Exercise" ADD CONSTRAINT "exercise_lesson_order_needs_lesson" CHECK ("lessonOrder" IS NULL OR "lessonId" IS NOT NULL);
```

Rules that need more than one table (owner type ↔ populated column, block kind ↔ populated field) are validated in the services; so are the classes' rules that cross tables — format ↔ capacity and a group's title, the capacity when a seat is added, a student once per class, a free seat never paid, a payment's `classCount` never below the seats that count, a reason on every staff mark, one `CLASS_ATTENDED` per student and class, and one lock order (every `Class` row first, by id, then the student's payments) — each in its writer ([Classes](/platform/classes)).

`prisma/exercise-migration.test.ts` reads it), `lesson_exercises` (hand-written, **moves data**: `Exercise.lessonId`/`lessonOrder` with their unique index, cascade and two CHECKs, `TrainingAttempt.isLegacy`; then every hand-made `TrainingExercise` — `NOT "isDerived"` — becomes an `Exercise` with the **same id**, SEQUENCE and PUBLISHED, titled after its lesson, its difficulty the course's easiest level's `eloMin` (else 1200), its solution PGN the frozen line over the frozen start — a FIND_MOVE keeps only its first SAN, where the trainer stopped —, its hash the SQL twin of `createPositionHash`, its topics the lesson's; its attempts are re-pointed and marked `isLegacy`, one `UserExerciseState` per student and exercise is built from them — count, first, first PASSED, last, last result; no review —, and the moved rows leave `TrainingExercise`, the derived drills staying. `prisma/exercise-migration.test.ts` holds the filter on every statement, the hash replica over the seed's start FENs and the writers' values. Applied to the local database on 2026-10-16 (4 exercises, 4 attempts, 2 states moved; 1 derived drill and its 4 attempts stayed); production only in a release made after the owner checks phase 2 locally, since a flag cannot undo a data move).

Workflow:

1. Edit `schema.prisma`, get the structural SQL with `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`, and write the migration by hand in a new dated folder, adding what Prisma cannot express (a CHECK, a partial index, a backfill, catalog rows). **Not `npm run db:migrate`**: a few old migrations were edited after being applied, so it asks to reset the local database — never accept.
2. `npm run db:deploy` against the local database (it writes to whatever `.env.local` points to: `npm run db:target` first, and an agent asks before running it), then `npm run db:generate`, `npm run typecheck`, and `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` must say «No difference detected».
3. Production: back up first (`pg_dump`), then `npm run db:deploy`. Migrations have no down path.
4. If the change needs data movement that SQL cannot do (reading PGN headers, for instance), write a script like `scripts/migrate-chapter-collections.ts`: short transactions, idempotent, resumable, with a `--dry` mode.

## Seed

`prisma/seed.ts` + `prisma/seed-data.ts`: idempotent (catalogs by `upsert(code)` — `seedCatalog` for `[code, label]` pairs, `seedCatalogRows` for a catalog with more columns, like `ContentType` —, domain rows by fixed ids or natural keys), seeds the topics roots first, so each tactical motif finds its parent, creates the three demo accounts, a course with chapters/lessons/exercises, studies and games (indexed with `indexGamePositions`), classes with blocks and a transcript, activities and rebuilt daily stats. **The seed is the one documented exception to the classes' single writers**: it writes the facts of a class (topic, date, status, marks) as data by fixed id, so re-seeding moves the dates without recording a reschedule, spreads the same pure functions the writers spread for the derived columns (`classScheduleColumns`, `classMeetingColumns`) and seats students through `syncClassSeat`, so the payment's invariant holds for the demo too. The same exception covers the exercises: a lesson's four exercises go by their fixed ids (the ones the `lesson_exercises` migration kept) spreading `exerciseSolutionColumns` over a PGN built with `solutionPgnFromLine`, PUBLISHED as seeded data, their orders cleared first by `planSeededOrders` over `Exercise_lessonId_lessonOrder_key`; the demo student's attempts at them are written `isLegacy`, as the migration left them, and `rebuildUserExerciseState` folds every state afterwards. `SEED_NOW` pins the reference instant. See [Scripts & seed](/operations/scripts-and-seed).
