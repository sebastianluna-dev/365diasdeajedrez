# Data model

`prisma/schema.prisma` describes the platform database. Prisma 7 setup:

- generator `prisma-client` with `output = "../lib/platform-db/generated"` (git-ignored; `npm run db:generate`) and `previewFeatures = ["relationJoins"]`, so reads can ask for `relationLoadStrategy: "join"` (see [Data access](/architecture/data-access));
- no `url` in the datasource: the CLI reads it from `prisma.config.ts` (`schema`, `migrations.path`, `migrations.seed = "tsx prisma/seed.ts"`, `datasource.url = PLATFORM_DATABASE_URL`), the runtime from `@prisma/adapter-pg` in `lib/platform-db/get-platform-db.ts`;
- `prisma.config.ts` loads `.env.local` and then `.env`.

## Design decisions

- **PGN is the content.** `Lesson.pgn`, `Game.pgn` and `ClassBlock.pgn` hold the chess material; there are no per-move tables. Positions, lines and diagrams are derived by `lib/chess` at read or index time.
- **Catalogs instead of enums.** Every restricted domain is a table with `id`, `code` (unique, stable), `label` (Spanish), `order` and sometimes `isActive`. Business logic compares `code`; the seed upserts them; TypeScript mirrors them in `constants/platform/*-codes.const.ts`. A catalog the **staff edits** (`Level`) is identified by a `slug` instead: no logic compares against its rows, so there is no code to keep stable.
- **Composite primary keys** for progress and join tables.
- **Roles by row existence** (`Teacher`, `Staff`).
- Constraints Prisma cannot express are written by hand in the migrations (below).

## Catalogs

`ContentType` (OPENINGS, TACTICS, CALCULATION, STRATEGY, PAWN_STRUCTURES, ENDGAMES, GAME_ANALYSIS, PREPARATION; besides `label` each row has a `shortLabel` for tags and a `description`, so the seed writes them with `seedCatalogRows`) · `CourseStatus` (DRAFT, PUBLISHED, ARCHIVED) · `AuthorRole` (CONTENT_AUTHOR, DIGITAL_ADAPTATION) · `SourceType` (BOOK, DIGITAL_COURSE, IN_PERSON_COURSE, VIDEO, ARTICLE, MAGAZINE, GAME_DATABASE, INTERACTIVE_STUDY, COACH_MATERIAL, OWN_MATERIAL, COMPILATION, OTHER — the kind of resource a course's material comes from) · `SourceEntityKind` (DIGITAL_PLATFORM, PUBLISHER, CONTENT_PROVIDER, OTHER) · `ContentRole` (INTRO, CLOSING) · `BoardOrientation` (WHITE, BLACK, AUTO — AUTO only for user settings) · `ExerciseMode` (REPRODUCE_LINE, FIND_MOVE) · `ProgressStatus` (NOT_STARTED, IN_PROGRESS, COMPLETED) · `AttemptResult` (PASSED, FAILED) · `AttemptContext` (LESSON, CHAPTER_QUIZ, TRAINER) · `OwnerType` (USER, COURSE, TEACHER) · `DatabaseKind` (MY_GAMES, TOURNAMENT, STUDY, COLLECTION) · `GameSource` (MANUAL, PGN_IMPORT, PLATFORM_GAME) · `GameResult` (WHITE_WINS, BLACK_WINS, DRAW, ONGOING; the label is the PGN token) · `ClassStatus` (SCHEDULED, LIVE, COMPLETED, CANCELLED) · `MeetingProvider` (ZOOM, MEET, OTHER) · `ClassBlockKind` (TEXT, VIDEO, GAME_REF, LESSON_REF, POSITION_REF, FILE) · `TranscriptStatus` (PENDING, READY, FAILED) · `ActivityType`, `SubjectType`, `StatMetric` (see Activity) · `Topic` (hierarchical via `parentId`: TACTICS, OPENING_LINE, PAWN_STRUCTURE, ENDGAME, STRATEGY…).

### `Level`: the editable catalog

Who a course is aimed at. It is the one catalog edited from the interface (`/administracion/niveles`), so it has no `code`:

| Field         | Meaning                                                                                                                    |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `slug`        | Unique; what `/cursos?nivel=` and the course form carry.                                                                   |
| `name`        | «Iniciación», «Principiante», «Intermedio», «Avanzado», «Experto», «Maestro».                                              |
| `description` | What is worked on at that level.                                                                                           |
| `order`       | Position by difficulty, the easiest first. Ties are broken by `eloMin` and by name.                                        |
| `eloMin`      | Inclusive lower end, never negative. «Iniciación» is `0`.                                                                  |
| `eloMax`      | Inclusive upper end; `null` = no upper bound («Maestro»: `2200`, `null`).                                                  |
| `isActive`    | A retired level is not shown to students nor offered by the filter; its `CourseLevel` rows stay. A level is never deleted. |

The platform ships with 0–799, 800–1199, 1200–1599, 1600–1999, 2000–2199 and 2200+. Three decisions are part of the model:

- **The ranges are orientative.** They are an internal classification, not official categories nor equivalences between FIDE, Chess.com and Lichess, and «Maestro» names the difficulty of the content, not a title. Every screen the student sees a range on says «El Elo es orientativo».
- **Nothing is restricted by Elo.** No read nor action compares a range with anything: `publishedCourseWhere` is still the only condition to open a course.
- **No rating of the student is stored**, so a missing rating cannot become a zero. A player without a rating belongs to whatever level their knowledge says. If a rating is ever added to `User`, it has to be nullable.

Levels are apart from the content types (what the course teaches) and from the sources (where its material comes from): three different tables, three different joins.

Adding a value to a catalog is a seed row, not a migration. Replacing a catalog is one: `content_types` (2026-09-27) turned the single `CourseType` of each course into rows of `CourseContentType` (OPENING → OPENINGS, ENDGAME → ENDGAMES) and dropped the old table. `editable_levels` (2026-09-27) updated the four rows of `Level` **in place** (`BEGINNER` → `principiante`…; «Experto» became 2000–2199), so their ids and every `CourseLevel` assignment survived, and inserted «Iniciación» and «Maestro» with `ON CONFLICT ("slug") DO NOTHING`, so nothing is duplicated.

## Constraints written by hand

The initial migration and later ones add what Prisma cannot express:

```sql
-- exactly one owner
ALTER TABLE "GameDatabase" ADD CONSTRAINT ... CHECK (("userId" IS NOT NULL) <> ("courseId" IS NOT NULL));
ALTER TABLE "Position"     ADD CONSTRAINT ... CHECK (("userId" IS NOT NULL) <> ("courseId" IS NOT NULL));
-- at most one reference per class block
ALTER TABLE "ClassBlock" ADD CONSTRAINT ... CHECK ((("gameId" IS NOT NULL)::int + ("lessonId" IS NOT NULL)::int + ("positionId" IS NOT NULL)::int) <= 1);
-- NULL topic must not duplicate rows
CREATE UNIQUE INDEX ... ON "UserStatDaily"("userId", "day", "metricId", "topicId") NULLS NOT DISTINCT;
-- one active teacher per student
CREATE UNIQUE INDEX "teacher_student_one_active" ON "TeacherStudent" ("studentId") WHERE "endedAt" IS NULL;
-- one default study per user (migration 20260904190000)
CREATE UNIQUE INDEX "game_database_one_default_per_user" ...
-- no two source entities differing only by case (migration 20260927130000)
CREATE UNIQUE INDEX "source_entity_name_ci" ON "SourceEntity" (lower("name"));
-- a level's Elo range is never negative nor upside down (migration 20260927140000)
ALTER TABLE "Level" ADD CONSTRAINT "level_elo_range" CHECK ("eloMin" >= 0 AND ("eloMax" IS NULL OR "eloMax" >= "eloMin"));
```

Rules that need more than one table (owner type ↔ populated column, block kind ↔ populated field) are validated in the services.

## Migrations

`prisma/migrations/` (2026-08-30 → 2026-09-27): `init`, `add_exercise_frozen_at`, `add_auth_sessions`, `add_teacher_staff_panels`, `add_game_positions`, `add_game_title`, `shorten_study_and_game_ids`, `chapter_slug_and_short_lesson_ids`, `numeric_student_ids`, `lesson_training`, `derived_exercise_flag`, `lesson_training_color`, `class_block_pgn`, `game_order`, `game_player_details`, `rate_limit`, `study_types_and_shares`, `daily_goal`, `lesson_game_reference`, `chapter_collections`, `simplify_lesson_metadata`, `content_roles`, `composite_indexes`, `content_types`, `course_sources`.

Workflow:

1. Edit `schema.prisma`, run `npm run db:migrate` (creates and applies a migration in development) or write the SQL by hand when the change needs a CHECK, a partial index or data movement. For index-only changes `npx prisma migrate diff --from-schema-datamodel <old> --to-schema-datamodel <new> --script` produces the SQL.
2. `npm run db:generate`, then `npm run typecheck`.
3. Production: back up first (`pg_dump`), then `npm run db:deploy`. Migrations have no down path.
4. If the change needs data movement that SQL cannot do (reading PGN headers, for instance), write a script like `scripts/migrate-chapter-collections.ts`: short transactions, idempotent, resumable, with a `--dry` mode.

## Seed

`prisma/seed.ts` + `prisma/seed-data.ts`: idempotent (catalogs by `upsert(code)` — `seedCatalog` for `[code, label]` pairs, `seedCatalogRows` for a catalog with more columns, like `ContentType` —, domain rows by fixed ids or natural keys), creates the three demo accounts, a course with chapters/lessons/exercises, studies and games (indexed with `indexGamePositions`), classes with blocks and a transcript, activities and rebuilt daily stats. `SEED_NOW` pins the reference instant. See [Scripts & seed](/operations/scripts-and-seed).
