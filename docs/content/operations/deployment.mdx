# Deployment & backups

## Assumptions

- The app is built for **Vercel**: `@vercel/analytics` renders only when `VERCEL=1`; logs are JSON lines on stderr; Payload's start cost matters on cold starts (GraphQL disabled for that reason).
- Two managed Postgres databases (`DATABASE_URI`, `PLATFORM_DATABASE_URL`) with `sslmode=verify-full`. In development they are two databases of a container instead: [Local database](/operations/local-database).
- Cloudinary for every image; delivery URLs use `f_auto,q_auto`, and `next/image` is limited to `res.cloudinary.com`.
- The public site is served from the static home (`revalidate = 3600`) plus dynamic blog pages; the platform is fully dynamic.

## Environment in production

Everything in `.env.example` except the seed and script helpers, with:

- `NEXT_PUBLIC_APP_ENV=production` (turns on GA and the Meta Pixel — only if their ids are set);
- `NEXT_PUBLIC_SITE_URL=https://365diasdeajedrez.com` (canonicals, sitemap, robots, OG images);
- `PAYLOAD_SECRET`, `DATABASE_URI`, `PLATFORM_DATABASE_URL`, Cloudinary credentials.

Never set `ALLOW_DEMO_SEED` in production.

## Release order

1. **Back up both databases** (`npm run db:backup`, below). Prisma migrations have no down path.
2. `npx prisma migrate status` to see what is really pending, then `npm run db:deploy` (`prisma migrate deploy`) against the production `PLATFORM_DATABASE_URL`. Both follow `.env.local`: `npm run db:target` says where it points before anything is run, and again after it is switched back.
3. Deploy the app, which here means **pushing `main`**: Vercel builds a Production deployment from every push to it, so steps 1 and 2 come before the push, never after (a coding agent asks before any push: [Coding agents](/conventions#coding-agents)). Two GitHub rulesets guard `main` since 2026-10-02: **«main: no force push, no deletion»**, with no exception, and **«main: CI must pass»** (the `verify` job), which the repository's admins bypass — so a direct push by the owner goes through with a «Bypassed rule violations» notice from the remote, and anyone else's push or pull request waits for CI. `npm run build` first runs `prisma generate`: `lib/platform-db/generated/` is git-ignored, so without it Turbopack fails with `Can't resolve './generated/client'`. Then `next build` prerenders `/`, the sitemap and static pages, so it needs read access to both databases at build time (which is why CI does not build).
4. If a migration needs data movement, run its script (`scripts/…`) after the deploy, with `--dry` first.
5. Payload schema changes: there are no committed Payload migrations; the CMS tables are synced by Drizzle push when `next dev` runs against the database. Do that before deploying a collection change, or introduce Payload migrations (`payload migrate:create`) when the team wants an explicit path.

## Backups

Neither database can be rebuilt from the code: the platform holds accounts, progress and annotated games; Payload holds the site and blog content.

```bash
npm run db:target   # which databases .env.local points at: host and name, never the URL
npm run db:backup   # both of them, into ~/Backups/365diasdeajedrez/<name>-<date>-<time>.dump
```

`db:backup` (`scripts/db-backup.ts`) dumps whichever two databases `.env.local` names, with the `pg_dump` of the development container — its version is pinned to the managed databases', so nothing has to be installed —, reads each dump back with `pg_restore --list` before calling it a copy, and writes it for its owner only, outside the repository: a dump carries the accounts and their password hashes. `--dir <folder>` changes where; a folder inside the repository is refused. By hand it is the same two commands:

```bash
pg_dump --format=custom --no-owner --file="plataforma-$(date +%Y%m%d-%H%M).dump" "$PLATFORM_DATABASE_URL"
pg_dump --format=custom --no-owner --file="payload-$(date +%Y%m%d-%H%M).dump"    "$DATABASE_URI"
```

Restore into an empty or test database:

```bash
pg_restore --no-owner --dbname="$URL" archivo.dump
```

A full restore drill has not been rehearsed yet (`IMPROVEMENTS.md` #63): do it once on a scratch database, note how long it takes, and record what the provider offers (automatic snapshots, retention).

## After a deploy

- `/` loads and shows the current CMS content; save a Global in `/admin` and confirm the change appears on reload.
- `/robots.txt` and `/sitemap.xml` use the production URL.
- Log in with a real account; open `/entrar` behaviour indirectly by visiting `/` while logged in (it must land on the role's home).
- Import a PGN and search a position (exercises the platform database, transactions and indexes).
- Watch the logs for `level: "error"` lines from `next.request` (uncaught request errors) and `rate-limit` (database failures).

## Logs

Structured JSON lines on stderr (see [Caching, errors & logging](/architecture/caching-errors-logging)). Filter by `scope`: `next.request`, `rate-limit`, `session`, `password`, `game-positions`. The `error.digest` matches what the platform error page shows to the user.

## Security headers

`next.config.ts` sets, on every route (Payload's panel included): `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Cross-Origin-Opener-Policy: same-origin` and a `Permissions-Policy` that switches camera, microphone and geolocation off. Vercel adds HSTS. COEP is not set: it would enable multi-threaded Stockfish but break the Cloudinary images.

### Content-Security-Policy

Three policies, all written by `contentSecurityPolicy()` in `lib/content-security-policy.ts` (tested in `lib/content-security-policy.test.ts`), and chosen on 2026-10-03: a nonce where the pages are rendered per request anyway, no nonce where they are static.

| Where                                                                                 | Sent by                                                                                                | Scripts                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The platform's prefixes (`PROTECTED_PATH_PREFIXES`) and the login (`/iniciar-sesion`) | `proxy.ts`, per request                                                                                | `'nonce-…'` and `'strict-dynamic'`: a fresh nonce every request, which Next reads from the policy the proxy puts in the request's headers and adds to every script it renders; the chunks those scripts load are trusted through them. An injected `<script>` has no nonce and does not run. No analytics on these pages. |
| The public site, everything else                                                      | `next.config.ts` (`sitePolicySource()` leaves the platform's paths and `/admin` out, by first segment) | `'self'`, `'unsafe-inline'` (the Google Analytics and Meta Pixel snippets) and their two hosts. A nonce here would make every page dynamic and lose the CDN's cache.                                                                                                                                                      |
| Payload's panel, `/admin`                                                             | `next.config.ts`                                                                                       | The site's, plus `https://cdn.jsdelivr.net`, where the JSON field's code editor (Monaco) loads itself from.                                                                                                                                                                                                               |

All three: `default-src 'self'`; styles `'self' 'unsafe-inline'` (React writes `style` attributes, which a nonce cannot cover); images from this origin, `data:`, `blob:` and `res.cloudinary.com` (plus the trackers' on the site); `connect-src` to this origin and `api.cloudinary.com`, where the browser uploads signed images (plus the trackers' beacons on the site); workers from this origin and `blob:`; `'wasm-unsafe-eval'`, because the engine compiles WebAssembly in its worker (the worker script is a public file, so it is served with the site's policy, which allows it too); `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`. In production, `upgrade-insecure-requests`; in development instead, `'unsafe-eval'` (React's debugging stacks) and websockets to `localhost` (editor tools such as Console Ninja).

A new external origin — a script, an image host, an API the browser calls — goes into the lists of `lib/content-security-policy.ts`, or the browser refuses it; the test reads the trackers' and the uploader's URLs from their source files and fails if their hosts are not there. Checked on 2026-10-03 in Chrome with a `securitypolicyviolation` listener: the site, the login, the dashboard after logging in, a game with the engine on and `/admin` without a single violation, in development and in production.

## Performance

Measure only against `npm run build && npm run start` (three Lighthouse runs, median). Known state on 2026-09-09: mobile performance 80 → 92 on `/`; the remaining cost is the number of blocking stylesheets on the home page (`IMPROVEMENTS.md` #70).

What they are, read on 2026-10-02 from the production build's manifests (`entryCSSFiles` of `.next/server/app/(frontend)/page_client-reference-manifest.js`): ten files, 49.9 KB. The layout's (`globals.css` and the font faces), the error boundary's (`site-message`), the header's and the footer's, which every public page shares; three the home page shares with one or two other routes — `EloTable` (with the mentor's page), `ChessBoardLazy` (with the mentor's page and a blog article) and the clock's dial (with `/reloj-de-ajedrez`) —; and the home page's own CSS, which Turbopack already merges, in the three runs those shared files cut it into: the hero to the mentors, the teacher to the FAQ, and the call to action. So merging the sections' stylesheets into fewer files would not remove a request, and `cssChunking: "graph"`, tried on 2026-09-09 and again with `requestCost: 200000`, gives the same files. What is left is the order the shared files are imported in, which would save one or two requests on HTTP/2 at the price of a page that imports what its sections draw with; it was left alone.
