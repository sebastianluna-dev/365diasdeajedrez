# Data access & server actions

## The triad

Every domain under `services/<domain>/` follows the same shape:

| File                  | Role                                                                                                                                                                                                                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `<domain>.service.ts` | Reads. Resolves the user through the DAL, queries Prisma or Payload with the authorisation inside the `where`, returns view types. Read functions that several sections call in the same request are wrapped in React's `cache()` so the query runs once per request.                            |
| `<domain>.mapper.ts`  | Pure translation from rows to view types: Spanish labels from catalog rows, formatted dates (`lib/format-spanish-date.ts`), percentages, hrefs from `lib/platform-routes.ts`. Also exports the Prisma `include`/`select` objects the service uses, so the row type and the mapper stay together. |
| `<domain>.types.ts`   | The UI contract. Sections import only from here. Types carry `code`s next to labels when the UI has to decide something (`kindCode`, `statusCode`).                                                                                                                                              |
| `<domain>.actions.ts` | Server actions (`"use server"`). Writes only.                                                                                                                                                                                                                                                    |

Domains: `articles`, `home`, `mentors`, `site-settings` (Payload); `auth`, `classes`, `courses`, `dashboard`, `game-explorer`, `game-positions`, `media`, `studies`, `study-goal`, `trainer` (student); `teacher`, `teacher-classes`, `teacher-students` (teacher panel); `staff`, `staff-classes`, `staff-courses`, `staff-payments`, `staff-students`, `staff-teachers` (staff panel); `shared` (pure rules and helpers used across domains).

## Clients

- **Prisma** — `lib/platform-db/get-platform-db.ts` returns a `PrismaClient` stored on `globalThis` (survives `next dev` hot reloads without exhausting connections), one per generated `PrismaClient` class. The bundler can evaluate the generated client in more than one chunk (render versus route handlers and server actions), each with its own class, and a single slot that replaced the client whenever the class differed closed the pool the other chunk was querying on ("Cannot use a pool after calling end on the pool" on every platform page). Keying by class keeps both alive and still gives a fresh client after `prisma generate`, which re-evaluates the module with a new class, so it no longer requires restarting the dev server. The client uses `@prisma/adapter-pg` with `PLATFORM_DATABASE_URL`; there is no `url` in `schema.prisma` (Prisma 7 puts it in `prisma.config.ts` for the CLI and in the adapter for runtime).
- **Relations in one round trip.** The generator enables the `relationJoins` preview feature, and with it **the join strategy is Prisma's default for every read**: a read with `include` or a nested `select` is one SQL query, its relations built as JSON in the same statement. Without it Prisma reads each included relation in a query of its own, and against a remote database each query is a full round trip (about 140 ms from a developer's machine to Prisma Postgres). Measured on 2026-10-03 with Prisma's query log against the local database: a class with its blocks is 3 queries, and 31 when `relationLoadStrategy: "query"` is forced on it. The reads that also say `relationLoadStrategy: "join"` (the session's `readSessionUser`, the studies) say what is already the default. The one case for `"query"` is a read that nests an unbounded list, whose rows the join strategy builds into one large JSON array (see `IMPROVEMENTS.md`).
- **Raw SQL only where the typed API cannot say it**, with `$queryRaw`/`$executeRaw` and bound values: the `UserStatDaily` upsert (its unique index is `NULLS NOT DISTINCT`), the rate-limit counter (`INSERT … ON CONFLICT`) and the dashboard's four statistics ranges, one `SUM … FILTER` each in a single query (`statRangeSumsQuery`) where Prisma's `groupBy` needed one query per range. The builder lives in the mapper, so a test reads the SQL and the values it binds.
- **Payload** — `lib/payload/get-payload.ts` memoises `getPayload({ config })`. Reads use the local API (`payload.find`, `payload.findGlobal`) and are cached between requests with `unstable_cache` + tags (see [Caching](/architecture/caching-errors-logging)).
- The seed and the CLI scripts build their own `PrismaClient` because the singleton is `server-only`.

## Authorisation inside the query

There is no "fetch, then check". Examples:

- `services/shared/published-content.ts` — `publishedCourseWhere`, `publishedChapterWhere`, `publishedLessonWhere`: chained into every student read **and write** (progress, trainer), so a POST with the id of a draft lesson does nothing.
- `services/shared/game-visibility-rules.ts` — `buildVisibleDatabasesWhere` / `buildVisibleGamesWhere`: own databases, collections of _started_ courses, collections shared by a teacher, plus (for teachers) the games of actively assigned students. `game-visibility.ts` binds them to the current user. Studies and the position explorer share these rules so the explorer can never list a game the student cannot open. What «Mis estudios» _lists_ is narrower: `buildListedDatabasesWhere` is the visible databases but a course's (`courseId: null`), so a course's collections stay openable and searchable without showing as studies of their own.
- `services/shared/exercise-visibility-rules.ts` — the one where-builder of the exercises: `buildSolvableExercisesWhere` (what a student may solve: the library, and a series given to them while its teacher is assigned to them, holding the series owner's usable exercise or one in the library now), `solvableInContextWhere` (the same, narrowed to the path an attempt claims), `buildPickableExercisesWhere` (what an author may put in a series: their own usable ones and the library, never another teacher's), `buildOwnExercisesWhere` and `teacherVisibleAttemptsWhere` (a student's attempts a teacher may see: in their own series, or in a neutral context at their own exercise or one that was ever in the library; never by current status). `exercise-visibility.ts` binds them to the current user and their active teacher.
- `services/studies/study-rules.ts` — `studyPermissionsOf({ kindCode, isOwner })`: the permissions table for studies (non-owners get nothing; `MY_GAMES` cannot be deleted or re-typed). Actions and UI use the same function.
- Teacher services put `teacherId` inside the `where`; `lib/platform-auth/guards.ts` adds `assertTeacherOwnsClass` and `assertTeacherCanReferenceGame` for writes (the teacher's writes about a class go through the writers of `services/shared/`, phase 2 of the classes rebuild), failing with `notFound()` so nothing confirms the resource exists.

## Server actions

Server actions are reachable by a direct POST, not only from the UI. Every action in the codebase follows this order:

```ts
"use server";

export async function updateStudy(studyId: string, formData: FormData): Promise<void> {
  const user = await getCurrentUser();                                   // 1. identity from the DAL
  if (!(await allowAction(`${user.id}:study-update`, 30, 60_000))) fail(…, "throttled"); // 2. rate limit
  const name = readText(formData, "name").slice(0, NAME_MAX_LENGTH);     // 3. bounded inputs
  if (!name) fail(…, "invalid");
  // 4. ownership + rules (study-rules, guards, published-content…) inside the write's where
  // 5. write, then revalidatePath(...)
}
```

- **Identity:** `getCurrentUser()`, `requireTeacher()` or `requireStaff()` as the first `await`. Never an id from the client.
- **Rate limit:** `allowAction(key, limit, windowMs)` in `lib/rate-limit.ts` keeps one counter per subject and operation in the `RateLimit` table with a single `INSERT … ON CONFLICT` statement, so the ceiling is global across instances and cold starts. If the database fails it lets the request through and logs it. Expired windows are purged from the app itself (1 % of calls).
- **Inputs:** a zod schema per action, read with `parseForm` (`services/shared/form-schema.ts`); PGN size and count limits in `constants/platform/content-limits.const.ts` (`PGN_MAX_LENGTH` 2 MB, `PGN_MAX_GAMES` 500, `PGN_IMPORT_TRANSACTION` with a 120 s timeout). The body limit of a server action is raised to 3 MB in `next.config.ts` (`experimental.serverActions.bodySizeLimit`) so that a PGN of that size reaches the action, which is who answers when it is too long: with Next's default of 1 MB the request was rejected first.
- **Errors:** redirect to the page with `?error=<code>`, built by `withErrorParam`; the page maps the code with `LOGIN_ERROR_MESSAGES`, `TEACHER_ERROR_MESSAGES` or `STAFF_ERROR_MESSAGES`. `services/shared/safe-return-to.ts` holds both: `withErrorParam` and `safeReturnTo`, which validates any client-supplied return path. Account creation and password reset return state via `useActionState` so a temporary password is displayed once and never travels in a URL, and since 2026-10-15 so does every form in a popup, with the states of `services/shared/form-state.ts` (the errors field by field, what was sent, or the notice of a success); a success a page says once travels as `?aviso=<code>[.arg…]` (`withNoticeParam`, `readNotice`), numbers or ids only ([Conventions › Server actions](/conventions#server-actions)).
- **Concurrency:** unique-constraint races are caught by name with `services/shared/prisma-errors.ts` (`isUniqueConstraintError(error, "teacher_student_one_active")`), which understands both the classic engine's `meta.target` and the pg driver adapter's `driverAdapterError` shape (the index's name, or the columns when PostgreSQL sends none) and compares whole names, never a name found inside another. Its test builds the P2002 with the installed `PrismaClient` and `@prisma/adapter-pg` over a `pg` client that never connects, so the adapter's shape is checked against the version in use, and fails on any other file that compares with `"P2002"` or reads `meta.target`.
- **Reordering:** `services/shared/reorder.ts` plans `planSwap`, `planDenseRenumber` and `planFullReorder` through a temporary out-of-range order (`TEMP_ORDER = -1`), because PostgreSQL validates `@@unique([parent, order])` row by row and a direct swap raises P2002 intermittently. Services execute the plan inside `$transaction`. `planMoves` is `planFullReorder`'s two passes for any set of targets; the seed's `planSeededOrders` (`prisma/seed-rules.ts`) builds on it to put its rows back in their order whatever the panel did.
- **Side effects:** `services/shared/user-activity.service.ts` appends to `UserActivity` and increments `UserStatDaily` in the same call; `services/game-positions/game-positions.service.ts` (re)indexes positions and receives the transaction client as a parameter so importing and indexing commit together.

## Client-side data

The platform has one route handler of its own (`app/(platform)/lecciones/[lessonId]/route.ts`, which redirects an old lesson URL) and no data client in the browser. When a Client Component needs data (the explorer board, autosave of a game PGN, the trainer recording an attempt, an upload signature) it calls a server action: `searchPosition`, `autosaveGamePgn`, `recordTrainingAttempt`, `createUploadSignature`. Those actions validate the input (FEN legality, PGN size, clamps) before touching the database.

## Payload-side data

The public site reads Payload with the local API inside services (`services/home`, `services/articles`, `services/mentors`, `services/site-settings`). Mappers convert Payload documents into plain view types (`services/shared/map-content-image.ts` turns a populated `Media` into `{ src, alt, width, height }`, throwing if the relationship was not populated, i.e. `depth` was too low).
