# Payload CMS

`payload.config.ts` builds the CMS that lives at `/admin` (UI) and `/api/*` (REST). It runs inside the same Next app but on its **own database** (`DATABASE_URI`) with its own users. GraphQL is disabled because nothing consumes it and building its schema is part of every Payload start (every cold start in serverless).

```ts
buildConfig({
  secret: process.env.PAYLOAD_SECRET,
  admin: { user: "users" },
  collections: [Users, Categories, Tags, Media, Articles],
  globals: [HomeHeader, HomeHero, HomeProgram, HomeTeacher, HomePackages, HomeFaq, HomeMentors, HomeReviews, HomeCta, SiteSettings],
  editor: lexicalEditor(),
  sharp,                                           // reads width/height of uploads; Cloudinary does the transformations
  upload: { limits: { fileSize: 5 * 1024 * 1024 }, abortOnLimit: true },
  graphQL: { disable: true },
  db: postgresAdapter({ pool: { connectionString: process.env.DATABASE_URI } }),
  plugins: [cloudinaryStorage({ …, folder: "365-ajedrez", collections: { media: true } })],
  typescript: { outputFile: "payload-types.ts" },
});
```

`payload-types.ts` is generated from this config (`npx payload generate:types`) and imported by the mappers; regenerate it whenever a field changes. `app/(payload)/admin/importMap.js` and `app/(payload)/api/[...slug]/route.ts` are generated by Payload too and must not be edited.

## Collections

| Slug | File | Purpose | Access |
| --- | --- | --- | --- |
| `users` | `collections/Users.ts` | CMS users with `role: admin \| editor`, `name`, `authorTitle` (shown next to the author in the blog). `auth: true`. | read/update: admin or self; create/delete: admin; only an admin can change `role` |
| `categories` | `collections/Categories.ts` | Blog categories with auto slug | read: anyone; write: any logged-in user |
| `tags` | `collections/Tags.ts` | Blog tags with auto slug | same |
| `media` | `collections/Media.ts` | Images (`image/*`) with required `alt` and optional `caption`; stored on Cloudinary | read: anyone; write: logged in |
| `articles` | `collections/Articles.ts` | Blog posts with **drafts/versions**. Tabs: *Contenido* (title, slug, excerpt, featured image, read time, Lexical `content`), *Organización* (author → users, categories, tags), *SEO* (`metaTitle`, `metaDescription`, `ogImage`); sidebar `publishedAt` | read: published only, or anything when logged in; write: logged in |

Hooks on `articles`: `beforeChange` stamps `publishedAt` the first time a document is published; `afterChange` and `afterDelete` call `revalidateArticlesAfterChange/Delete` (tag `articles`, `/blog`, `/blog/[slug]`, `/sitemap.xml`).

The Lexical editor for articles enables headings, paragraphs, bold/italic, links, lists, blockquote, horizontal rule, uploads and the custom blocks below.

## Globals

All Globals are readable by anyone and writable by any logged-in CMS user; each one's `afterChange` hook revalidates the pages that show it.

| Slug | File | Content | Hook |
| --- | --- | --- | --- |
| `home-header` | `globals/HomeHeader.ts` | `navItems` blocks: `navLink` (label, href) and `navDropdown` (label + links) | `revalidateHeader` |
| `home-hero` | `globals/HomeHero.ts` | H1, description, image, CTA | `revalidateHome` |
| `home-program` | `globals/HomeProgram.ts` | Section title/description and modules | `revalidateHome` |
| `home-teacher` | `globals/HomeTeacher.ts` | Tabs with the teacher's info, photo and a featured game (PGN) | `revalidateHome` |
| `home-packages` | `globals/HomePackages.ts` | Pricing packages (name, price, previous price, currency, period, features…) | `revalidateHome` |
| `home-faq` | `globals/HomeFaq.ts` | Eyebrow, title and Q&A items | `revalidateHome` |
| `home-mentors` | `globals/HomeMentors.ts` | Mentors with short/long FIDE titles, slugs, bios and games; feeds `/mentor/[slug]` | `revalidateHome` |
| `home-reviews` | `globals/HomeReviews.ts` | Testimonials | `revalidateHome` |
| `home-cta` | `globals/HomeCta.ts` | Floating CTA texts | `revalidateHome` |
| `site-settings` | `globals/SiteSettings.ts` | WhatsApp country code, local number and default message (footer and CTA) | `revalidateSiteSettings` |

## Blocks

Reusable block definitions in `blocks/`:

- Article content: `image-block` (media + alt + caption), `callout-block` (title, content, type info/tip/warning), `chess-diagram-block` (FEN, caption, orientation), `chess-game-block` (PGN, title, players, event, date).
- Navigation: `nav-link-block`, `nav-dropdown-block`.

Each block declares an `interfaceName`, so `payload-types.ts` exports a TypeScript interface per block and the renderers in `components/sections/blog-article/article-content/blocks/` switch on the block slug.

## Access helpers and the slug field

`lib/payload/access.ts`: `anyone`, `isAdmin`, `isAdminFieldAccess`, `isAdminOrEditor` (any logged-in user), `isAdminOrSelf`, `isPublishedOrLoggedIn` (`_status = published` for anonymous requests).

`lib/payload/slug-field.ts` returns a unique, indexed `slug` field that is generated from a source field (`title`, `name`) **only the first time** the document is saved with an empty slug, and de-duplicated with `-2`, `-3`… suffixes. Editing the title later never moves a public URL.

## Media storage

`lib/payload/cloudinary-adapter.ts` is a small self-owned adapter for `@payloadcms/plugin-cloud-storage` (there is no official Cloudinary adapter):

- `handleUpload` streams the buffer to Cloudinary with `public_id = <folder>/<filename without extension>` and `resource_type: auto`;
- `generateURL` returns the Cloudinary delivery URL with `f_auto,q_auto`;
- `disablePayloadAccessControl: true` makes Payload store that URL instead of proxying files through `/api/media/file/...`;
- `staticHandler` redirects (302) to Cloudinary for any legacy `/api/media/file/<name>` request.

`sharp` is configured only so Payload records `width`/`height` on upload; the site uses them to keep image aspect ratios (`services/shared/map-content-image.ts`). Images uploaded before `sharp` was added have no dimensions until they are re-uploaded.

## From an edit to the site

1. An editor saves a Global or publishes an article in `/admin`.
2. Payload runs the `afterChange` hook inside its API request: `revalidateTag(tag, { expire: 0 })` and `revalidatePath(...)`.
3. The next visit to `/`, `/blog` or the article renders with fresh data; nothing waits for the one-hour safety window.

## Operational notes

- No Payload migrations are committed; Drizzle push keeps the CMS tables in sync while running `next dev` against the database.
- The 5 MB upload cap applies to the whole CMS; it is a safety net for editors who export heavy photos.
- Preview/live preview of drafts is not wired (`IMPROVEMENTS.md` #52).
