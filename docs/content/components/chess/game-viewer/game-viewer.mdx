## Purpose

**The** platform's game viewer. Lessons, the studies' games, class blocks, the teacher's view of a student's game and the two position pickers all mount this same component. Do not create parallel viewers: a new need is a new prop here, given as data.

It renders a board with a notation panel next to it, the four navigation buttons plus flip, an options menu (sound, fullscreen), optional player strips, an optional engine with an evaluation bar, and props for what each screen needs around it: a title and a badge, the way on under the board (`onwards`, given as data), and a live game against a bot (`interaction="play"` with `play`). Its two old slots (`footerActions`, `positionActions`), older than the data-not-components rule and used by no screen, were removed on 2026-10-08 when the play mode came in. With `editable` and `onPgnChange` it becomes an in-place editor: moves are played on the board, arrows are drawn, right-clicking a move opens its menu. There is no separate editing screen; the game is annotated where it is read.

The viewer never saves and never fetches. It receives a PGN, reports the current path and, when editing, reports the new PGN; the screen that mounts it owns persistence.

## Behaviour

**Tree and current path.** `parsePgnTree(pgn)` is memoised. The current path is `path ?? selectedPath`, resolved at render time to the closest existing ancestor when the PGN changed underfoot (an undo, a deleted branch), so there is never a frame with the board at the start. Every path change is both stored and reported through `onPathChange` (kept in a ref so the parent need not memoise). An unparsable PGN renders a single error paragraph with the `_state_error` modifier.

**Layout.** The gap between the board and the notation is `--viewer-column-gap` (`--platform-space-6`, 24px, by default), which a screen that wants the board to breathe widens — the lesson sets it to `--platform-space-12` (48px), the same air it leaves on the board's other two sides.

The notation's column measures what the BOARD's row does (`height: 0` plus `min-height`, so an auto row cannot be stretched by a long game), less whatever `--viewer-panel-trim` says: a screen where the buttons sit under the board sets it, and the panel then ends at the board's own bottom edge instead of running down beside them. The lesson sets it to 0 since 2026-10-22: its column of notes runs down beside the keys, to the foot of the panel. Everywhere it is 0. A screen can also raise the column's floor, 320px, through `--viewer-panel-min`: the lesson asks for 384, and the board gives way.

The board's track is `minmax(0, var(--viewer-board-max, 600px))` and the notation's `minmax(320px, 1fr)`: the notation never goes under 320px — with the board sized by the height, a tall window would let it eat the whole row — and not a px more than that, because every px held back there is a px the board cannot use to fill the height it was given.

**Navigation.** Four square keys, 48px each, white over the page's grey with no line around them (they were closed by an inset hairline until 2026-10-05, which the owner took out); one that leads nowhere — at the start of the game, or at its end — sinks into the page (`--platform-track`) instead of doing nothing when pressed. Their icons are in the muted grey, the platform's one grey for a neutral icon on white (2026-10-07: in the text's ink the keys read black), «next» too, which until then went in the text's ink as the key pressed 90 % of the time (`_emphasis_strong`) and which the owner wanted like the rest; under the pointer every key takes the accent's ink. They do not stretch: they are pressed one after another, and a stretched button is a target one has to aim at. In the studies panel, where no way-out button follows them, they are centred under the notation.

First, previous, next, last read the current path from a ref so holding "previous" or "next" keeps traversing: 400 ms before the repeat starts, then one move every 130 ms, stopped on pointer up, leave or cancel. Arrow keys work only while the viewer is at least 60 % in view or has been clicked (there may be several on a page) and never while typing in an input, textarea or contenteditable. An arrow also **lets go of the focus** when it is on a move: the move that was clicked keeps it, and the first arrow makes the browser draw its focus ring around a move that is no longer the one being looked at. Whoever reached a move with Tab keeps their ring, because that is where they are.

**Flip, sound, fullscreen.** Flip is a game action and sits with the navigation buttons. Sound and fullscreen are viewer settings and live in the options menu (`role="menu"`): opening it moves the focus to the first option, Up and Down walk the options and wrap around, Escape and choosing an option close it and hand the focus back to the button, an outside click closes it without touching the focus. It unfolds upwards from the button and folds back: closed, it stays mounted for 120 ms through [`useLingering`](/components/chess/game-viewer/use-lingering-hook) with `.game-viewer__options-menu_state_closing`, unpressable, and the same hook keeps the [`MoveContextMenu`](/components/chess/game-viewer/move-context-menu) for its exit. The sound toggle is a `menuitemcheckbox` backed by [`viewer-preferences`](/components/chess/game-viewer/viewer-preferences) through `useSyncExternalStore`, so every viewer on the page shares it and the server paint uses the default. Fullscreen state is read from `document.fullscreenElement` on `fullscreenchange`, because Escape leaves it without the button. A move sound plays on position change (capture when the piece count drops), never on mount.

**Height.** The notation column measures what the board does, never what the game does. The two share one `auto` grid row, which would otherwise grow to the taller of them, so `.game-viewer__panel-column` has `height: 0; min-height: 100%`: it contributes nothing to the row, the board alone sets it, and the column then takes that whole row. The move list scrolls inside the card and the engine, switched on, takes room from the list instead of pushing the card below the board. Full screen undoes it (`height: auto`), because there the row is `1fr` of the screen.

**Engine.** `useEngine(fen, engine && engineOn)` lives here and not in the panel because two far-apart places consume it: the evaluation bar next to the board and the panel's lines. The bar's slot is reserved whenever `engine` is true so switching it on does not move the layout; it fills from the bottom with White's advantage. `engineExpanded` is tracked here because the height an expanded line takes is given up by the notation.

**Editing.** `isEditing = editable && Boolean(onPgnChange)`. Then the board becomes interactive with editable shapes, `onMove` calls `editing.addMoveAt`, `onShapesChange` calls `editing.updateShapes`, and both move lists receive `onContextMenu`, which opens the [`MoveContextMenu`](/components/chess/game-viewer/move-context-menu) with `canPromote` and `canPromoteOneStep` derived from the path (all-zero segments means main line; last segment `0` means first sibling). Comment and annotate items are offered only when the viewer has `tools` (the panel they lead to) and never in fullscreen. All mutations go through [`usePgnEditing`](/components/chess/game-viewer/use-pgn-editing-hook).

**Development aid.** Outside production, PGN warnings (illegal moves) are listed at the top so an author can fix the source.

## Markup & styling

No white box of the viewer — the notation panel, the tools card under the board, the two player strips and the evaluation bar — is outlined: each is white on the page's grey (`--platform-bg`), over its shadow where it has one. They were outlined by the thin grey while the page was white, which is what the outline was for. What floats over a card — the options menu, the moves' context menu — keeps its border.

Block `.game-viewer` (924 lines), the largest sheet in `components/`.

**The new design system's look** (`look="material"`, `.game-viewer_look_material`, 2026-10-22): the board rounded at 8px, the keys 4px apart, the panel with no card of its own (no fill, shadow or rule under the head), the title in the display font at weight 500, «Prioridad» an amber pill (`--platform-m3-warning-container`), and the notation in the move tree's own material look (`look` is passed on to [`MoveTree`](/components/chess/game-viewer/move-tree): moves as pills, the one on the board in the primary), its text at `--platform-type-md`.

**The board's column is a whole number of eights wide** (2026-10-05): `.game-viewer__board-card` is `round(down, 100%, 8px)` of its track, and the full-screen board's side is rounded the same way. Chessground rounds its board down so that every square is a whole number of device pixels — to 8px at a pixel ratio of 1, to 4px on a retina screen —, so on a track of 743px the board came out 736 or 740 wide under player strips of 743: the strips stuck out past the board's right edge and a sliver of the page showed between the board and the strip under it. On a width that is already a multiple of 8, chessground has nothing left to round at any whole pixel ratio, and the strips, the board and what stands in for it while it loads ([`BoardSkeleton`](/components/platform/shared/board-skeleton)) are one width. What the track has left over, 7px at most, joins the gap before the notation; on a phone, where the board is the window's width, the card is centred.

## Usage

Read-only, from `components/platform/sections/courses/lesson-view/lesson-board.section.tsx`:

```tsx
import { GameViewer } from "@/components/chess/game-viewer/game-viewer.comp";

<GameViewer
  pgn={lesson.pgn}
  orientation={lesson.orientation}
  moveList="flow"
  title={lesson.name}
  badge={lesson.isPriority ? "Prioridad" : undefined}
  boardTools={false}
  onwards={{
    skipHref: lesson.nextLessonHref,
    skipLabel: "Saltar",
    skipTitle: "Pasar a la siguiente lección sin marcar esta",
    finishLabel: "Continuar",
    finish: completeLesson.bind(null, lesson.id),
  }}
/>;
```

Editing, with the engine, the players and the tools, from `components/platform/sections/studies/game-view/game-view.section.tsx`:

```tsx
<GameViewer
  pgn={pgn}
  controls="panel"
  engine
  editable={game.canEdit}
  onPgnChange={applyPgn}
  players={{
    white: { name: game.white, elo: game.whiteElo, title: game.whiteTitle, country: game.whiteCountry },
    black: { name: game.black, elo: game.blackElo, title: game.blackTitle, country: game.blackCountry },
  }}
  tools={{ saveLabel }}
/>
```

Nothing is passed as JSX: the section holds the PGN (two things write it and the autosave reads it) and the viewer owns the path, the tools' tab and the strips.
