# `LessonFrame`

|            |                                                                                     |
| ---------- | ----------------------------------------------------------------------------------- |
| File       | `components/platform/sections/courses/lesson-view/lesson-frame.comp.tsx`            |
| Kind       | Server Component                                                                    |
| Stylesheet | `lesson-frame.comp.css` → block `.lesson-frame`                                     |
| Used by    | `app/(platform)/cursos/[courseRef]/[chapterOrder]/(lesson)/layout.tsx`              |
| Composes   | [`LessonOutline`](/components/platform/sections/courses/lesson-view/lesson-outline) |
| Uses       | `ChapterOutline` from `services/courses/courses.types`                              |

## Purpose

The screen a lesson is read on: the column of lessons and, beside it, the lesson.

It is mounted by the **chapter's** layout, and that is the whole reason the lessons hang from `/cursos/<curso>/<capítulo>/<lección>`. A layout is fetched once and is not rendered again while one moves inside it, so going from one lesson to the next costs its PGN and nothing else: the column is not queried, not drawn, not scrolled back to the top, and the board is the only thing that blinks.

It takes `children` because it is a container and nothing else — the exception the conventions allow. What goes in them is [`LessonBoardSection`](/components/platform/sections/courses/lesson-view/lesson-board-section), or [`LessonSkeleton`](/components/platform/sections/courses/lesson-view/lesson-skeleton) while that is on its way.

## Props

| Prop       | Type             | Required | Meaning                                                                                                                                 |
| ---------- | ---------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `outline`  | `ChapterOutline` | yes      | The course, the chapter and its lessons: what the column lists. It names no lesson, because the layout does not know which one is open. |
| `children` | `ReactNode`      | yes      | The lesson's own segment.                                                                                                               |

## Markup & styling

Block `.lesson-frame`. A grid of two tracks, `--platform-space-12` (48px) apart — 48 between the column of lessons and the board (this gap), and **24** above the board (the shell's top padding, `--platform-space-6`) and between the board and the panel of text (`--viewer-column-gap`, the same token): the board and its notes read as one piece, close under the bar, as in the design the lesson was drawn after (2026-10-06; both were 48, and the board grew by 24 with what they gave back). The outline is fixed to the window and takes no room in it, so the first track only **reserves** its width — `calc(var(--outline-width) - 40px)`, the 40 standing for the side padding the frame gives the page, which the panel covers on its way to the left edge — and `.lesson-frame__main` names its column (`grid-column: 2`) because an out-of-flow sibling does not take the first one by itself. That side padding is `--platform-space-12` (48px), not 40, so the track runs 8px past the panel and the board stands 56px from it rather than 48.

**The page is the window.** The layout's own `<div>` carries `.platform-page`, `.lesson-page`, `.platform-page_width_full`, `.platform-page_height_screen` and `.platform-page_scale_base` (the lesson keeps the base type and space scale from 1536px too, where every other page takes a step up: see [Styling](/ui/styling#type-and-space)): no cap on the width, and the frame hands it exactly what is left under the bar (see [`PlatformShell`](/components/platform/sections/shell/platform-shell-section)). Nothing here scrolls the page — the column of lessons and the panel of text each move on their own — because what is looked at is a board, and a board that falls below the fold is a board nobody sees whole.

So the board is measured by the **height** that is left, not by the width, and that height is **read off the column itself**: `.lesson-frame__main` is a size container (`container-type: size`; the grid stretches it to the frame's height, so what it holds never sizes it), and `--viewer-board-max` is `max(320px, calc(100cqh - var(--lesson-board-footer)))`, with no ceiling. `--lesson-board-footer` is what the board's footer takes under it, the 48px of its buttons plus the card's `--platform-space-4` gap, and it is also the `--viewer-panel-trim` that ends the panel of text where the board ends. Until 2026-10-06 the board was `100vh - 192px`, a sum of the bar, the shell's padding and the footer written by hand; those had grown to 206px (more at 1536px, where the shell's padding steps up), and the buttons under the board were cut off at the bottom of the window. Measured on the running app at 1366×768, 1440×900, 1536×760, 1600×900, 1920×1080 and 2560×1300: the buttons end inside the window and the page does not scroll. At `(width < 1280px)` or `(max-height: 620px)` it becomes one column, the board gets a flat `600px` back and the outline drops under the lesson.

**Elements:** `.lesson-frame__main`

No modifiers.

**Variables it hands down:** `--outline-width`, `--lesson-board-footer` (its own), `--viewer-board-max`, `--viewer-column-gap`, `--viewer-panel-trim`. In the one-column layout the main column goes back to `container-type: normal`: the page scrolls there and the column is as tall as what it holds, which a size container would collapse to nothing.

## Usage

From `app/(platform)/cursos/[courseRef]/[chapterOrder]/(lesson)/layout.tsx`:

```tsx
const outline = await getChapterOutline(courseRef, order);
if (!outline) notFound();

<div className="platform-page lesson-page platform-page_width_full platform-page_height_screen platform-page_scale_base">
  <LessonFrame outline={outline}>{children}</LessonFrame>
</div>;
```
