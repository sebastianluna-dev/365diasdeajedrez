# Convenciones del proyecto

Resumen de lo que explica `README.md` («Architecture in brief»). Si algo de aquí y el código discrepan, manda el código.

- **Tres piezas en una app Next 16**: sitio público `app/(frontend)`, CMS Payload `app/(payload)` (`/admin`, base `DATABASE_URI`) y plataforma autenticada `app/(platform)` + `app/(auth)` (Prisma 7 sobre `PLATFORM_DATABASE_URL`, una base distinta y sin tablas compartidas).
- **Datos**: la UI nunca llama a Prisma; siempre `services/<dominio>/{service,mapper,types}.ts` (más `.actions.ts` para server actions). Catálogos con `code` en vez de enums, y ninguno se edita desde la interfaz; `Level` se identifica por `slug`, que es por lo que se filtra el listado de cursos. El PGN es la fuente del contenido ajedrecístico. **Una columna derivada la escribe una única función compartida de `services/shared/`** que recibe el cliente de Prisma como primer parámetro, para correr dentro de la transacción de quien escribe (`syncLessonTrainingExercise`, `syncCatalogJoin`, `syncChapterDuration`); nadie más la toca, y el comentario de la columna en `schema.prisma` nombra a su único escritor.
- **Auth**: `lib/platform-auth/current-user.ts` es el DAL; toda página y server action de la plataforma resuelve al usuario ahí, nunca desde el cliente. `requireTeacher()`/`requireStaff()` abren cada página y action de `/profesor` y `/administracion`. `proxy.ts` sólo mira si existe la cookie. Una ruta nueva de `app/(platform)` se añade a `PROTECTED_PATH_PREFIXES` y al matcher del proxy (`proxy.test.ts` lo vigila).
- **Archivos**: kebab-case con sufijos `.comp.tsx`, `.section.tsx`, `.hook.ts`, `.const.ts`; named exports (default sólo en archivos de App Router); sin barrels, imports `@/...`.
- **Formularios de la plataforma**: los controles van sobre [Radix Primitives](https://www.radix-ui.com/primitives) (paquete `radix-ui`, sin estilos: se dibujan con nuestro BEM y tokens, nunca Radix Themes) a través de las piezas de `components/platform/shared/`: `PlatformForm`/`PlatformFormField`/`PlatformFormGroup` (formulario, campo con mensajes de validez y campo de grupo), `PlatformSelect`, `PlatformChoiceCards` (radio dibujado como tarjetas) y `PlatformCheckCards` (casillas dibujadas como tarjetas, para elegir varias). Un formulario nuevo usa esas piezas; los que aún usan `FormField` con controles nativos se migran cuando se tocan. Los `<select>` nativos ya no existen en la plataforma: todo desplegable es `PlatformSelect` (con `size="compact"` dentro de `FormField`, `emptyOption` para la opción «ninguno» que envía `""`, `groups` en vez de `<optgroup>`). El `<dialog>` sigue siendo nativo, y por eso el select no se porta a `<body>`. Un control que guarda su propio valor (`defaultValue`) sobre una primitiva de formulario de Radix se monta bajo `savedValueKey(defaultValue)`: React reinicia el `<form action>` al terminar la acción y la primitiva vuelve al valor que tenía AL MONTARSE, que en un formulario que sigue en pantalla es el de antes de guardar.
- **Componentes**: Server Components por defecto; `"use client"` sólo en la hoja que tiene el estado. **Un componente nuevo recibe datos, no componentes**: nada de props de tipo `ReactNode`/`ReactElement` que la página rellena con JSX (`editGame={<EditGame …/>}`, `studyTools`, `share`…); el componente recibe el modelo (`study`, `game`, los catálogos) y decide él qué monta y bajo qué permiso. La única excepción es `children` en un contenedor cuyo único trabajo es colocar lo que le den (un layout, una tarjeta, un diálogo). Si una parte necesita estado, se parte por dueño del dato: la envoltura queda en el servidor y sólo la hoja con estado es cliente (`GameAside` + `GameList`), nunca se convierte todo en cliente para poder pasar huecos. Los componentes anteriores a esta regla que aún tienen huecos (`GameViewer` con `skip`/`footerActions`/`positionActions`, `PlatformFormField` con `children` obligatorio) se rehacen cuando se toquen. Imágenes con `next/image`, nunca `<img>`. Copy en español. `components/` es espejo de `app/`: `site/`, `platform/` y `auth/`, cada uno con `sections/` (secciones de página) y `shared/` (piezas que reutilizan varias secciones de ese producto); `chess/` e `icons/` son de todos. Sin carpetas `common`.
- **Idioma**: **todo comentario va en inglés**, esté donde esté: código, CSS, tests, scripts, `prisma/schema.prisma`, workflows, `.env.example`, `.gitignore` y cualquier otro archivo de configuración; como los identificadores. El copy que ve el usuario (y las URLs) sigue en español, así que un comentario que cite un rótulo lo cita tal cual. Única excepción: los archivos generados (`payload-types.ts` reproduce las descripciones de los campos del CMS, que son copy) no se tocan a mano.
- **CSS**: BEM estricto (`bloque__elemento`, modificador `_clave_valor`), un archivo por componente y TODAS sus reglas anidadas bajo el selector raíz con nesting nativo (`&`), media queries dentro del bloque, desktop-first. Excepción: `@keyframes` no se puede anidar y va al nivel superior, con el nombre del bloque como prefijo. **Movimiento reducido**: toda hoja que anima apaga cada animación suya bajo `prefers-reduced-motion: reduce` (`animation: none`, o un instante si el componente espera el `animationend`), el scroll suave va sólo bajo `no-preference`, y el código que pasa `behavior: "smooth"` mira antes la preferencia con `matchMedia`; lo vigila `components/reduced-motion.test.ts`. Todo popup entra y sale animado (160 ms de entrada, 120 de salida, ambos apagados bajo `prefers-reduced-motion`): los `<dialog>` lo heredan de `.platform-dialog`; un menú que se monta condicionalmente se mantiene montado durante la salida con `useLingering` (`components/chess/game-viewer/use-lingering.hook.ts`) y un modificador `_state_closing`; una lista de Radix anima sobre `data-state`. Tokens `--color-*` (`app/(frontend)/globals.css`) y `--platform-*` (`app/(platform)/platform.css`). **La plataforma tiene dos temas**: cada color `--platform-*` se declara como `light-dark(<claro>, <oscuro>)` en el único bloque `:root` de `platform.css` — un color se añade o se corrige en una línea — y quién decide cuál se usa es `color-scheme` en `:root` (`light dark` por defecto, `light`/`dark` cuando `:root[data-theme]` dice que la persona eligió). `color-scheme` va en el MISMO elemento que los tokens: Lightning CSS traduce `light-dark()` a variables auxiliares que declara junto al `color-scheme`, y un elemento más abajo no llegan a los tokens (la plataforma se queda sin ningún color). Ninguna hoja nombra un color: dicen «el acento». **Texto y fondo**: un texto llega a 4,5:1 sobre lo que se escribe, en los dos temas; el gris sutil (`--platform-text-subtle`) es sólo para las superficies blancas (`surface`, `surface-soft`), y sobre un relleno gris o teñido (`bg`, `surface-neutral`, `surface-sunken`, el suave y el lavado del acento) se usa `--platform-text-muted`. Que cada color sea un par, que todo token usado esté declarado y el contraste los vigila `components/platform/platform-tokens.test.ts`. Sin Tailwind ni CSS-in-JS.
- **Esquinas de la plataforma**: en `app/(platform)`, `app/(auth)`, `components/platform`, `components/auth` y `components/chess` (las piezas de ajedrez son de todos, pero se dibujan con los tokens de la plataforma) un `border-radius` sólo puede ser **`8px`, `4px` o completo** (`1000px`; `50%` en un círculo), sea lo que sea: tarjeta, botón, campo, etiqueta, diálogo, menú. Nada de 6, 10, 12 o 16px «porque la tarjeta es grande». El `4px` es **sólo para un control de unos 20px o menos** — una casilla a 8px es casi un círculo, y un círculo se lee como un radio, como algo de lo que se elige uno; en cualquier cosa de tamaño normal es inventarse un radio, que es justo lo que la regla evita. `0` e `inherit` valen porque no dibujan un radio propio. Lo vigila `components/platform/border-radius.test.ts`.
- **Deuda**: lo que se encuentra y no se arregla va a `IMPROVEMENTS.md` (área, prioridad y cómo abordarlo); las tareas mecánicas, a `TODOS.md`; los riesgos que el proyecto asume a sabiendas (una licencia dudosa, por ejemplo), a `WARNINGS.md` con qué es, por qué se aceptó y cómo dar marcha atrás. Los tres están en inglés y **sólo existen en la copia local**: están en `.gitignore` y nunca van al remoto, así que un clon nuevo no los tiene.
- **Documentación**: la larga, en inglés, vive en `docs/` (sitio Nextra con su propio `package.json`; `cd docs && npm run dev`). **Todo cambio importante se documenta en el mismo commit**, no después: comportamiento, convenciones, rutas, modelo de datos, scripts, variables de entorno o una decisión que merezca quedar escrita. La página de `docs/` que cubra el área tocada; `README.md` (la referencia rápida del repositorio, en inglés) si cambian puesta en marcha, scripts o rutas; `AGENTS.md` si el cambio ES una convención; `IMPROVEMENTS.md`/`TODOS.md` para la deuda encontrada o resuelta.
- **Agentes (Claude Code)**: `.claude/settings.json` es la política del repositorio y sólo restringe (ninguna regla `allow`). **Nunca**: leer ni editar `.env.local` ni `.env` (se editan a mano), `prisma migrate reset`, `prisma db push`, borrar volúmenes de Docker ni forzar un `git push`. **Pregunta siempre**, también en modo auto, antes de un `git push` o de fusionar un PR (cada push a `main` despliega Producción en Vercel), de los scripts que escriben en la base a la que apunte `.env.local` (`db:deploy`, `db:seed`, `user:create`, `user:password`, `collections:by-chapter`), de reescribir o descartar historia (`filter-branch`, `filter-repo`, `reset --hard`, `clean`) y de tocar la propia política. Commits y PRs sin atribución de Claude. Un push, sólo cuando el dueño lo pide, y antes van la copia de las dos bases y `npm run db:deploy` en producción. Las reglas personales van en `.claude/settings.local.json`, que git ignora; la lista completa y sus límites, en `docs/` → Conventions.
- **Antes de dar algo por terminado**: `npm run format:check`, `npm run typecheck`, `npm run lint` y `npm test` en verde (los cuatro pasos de CI, en su orden: si uno falla, CI ya no corre los siguientes; `npm run format` arregla el formato), y la documentación del área tocada actualizada (si cambiaron páginas de `docs/`, `cd docs && npm run build`). Rendimiento, siempre contra `npm run build && npm run start`, nunca contra `next dev`.
